# release

## 目的と終わりの状態

GitHub release を公開して、利用者と下流の消費者（API を呼ぶ側、出力や設定に依存するサービスなど）が release note から何が変わり自分に何が要るかを判断でき、tag・本文・外部の文書が同じ release を指し、ユーザーが公開するものを理解したうえで承認している状態にする。

終わったと言えるのは、publish が済み、次を確かめて報告したとき。

- tag が対象 commit を指している。対象 commit とは、release PR のマージで main にできた commit（RELEASING.md が別の commit を指せばそれ）
- 公開された本文（後ろに付けた自動生成の節を除く）が、ユーザーが承認した文面（最終言語が日本語なら校正した原文、そうでなければその訳）と一致している
- 公開で起動するワークフロー（配布、デプロイ、通知）が起動し、失敗があればユーザーに示している
- RELEASING.md が指す外部の文書が、公開された release と同じ版・同じ変更を指し、release へのリンクが辿れる
- 既存の取り決めが下流の消費者への知らせを求めていれば、承認した文面で知らせた

## 進め方の前提

- 読み手は、自分に影響があるか、何をすべきかを決めるために読む。PR のタイトルや commit の列挙はその問いに答えない。本文は、変更を読み手への影響で語る。物差しは [references/release-notes.md](references/release-notes.md) にある
- publish と tag は取り消しにくい。publish は release を watch する人に通知し、`release` イベントで起動するワークフローを走らせ、immutable releases が有効なら tag と asset を固定する。本文は後から編集できるが、編集で通知が再送されるという記載は文書に無く、読み手は最初の版を読むものとして扱う。だから、公開の前にすべてをそろえ、公開の後に黙って直さない
- draft release は、tag を作らず、通知もワークフローも起こさず、write 権限のある人にしか見えず、消せる。公開されるそのものを、消費者が見るのと同じ描画で確かめる場にする
- ユーザーの判断は 2 つに集約できる。「この範囲・この版で、この内容を言う」と「公開されるものはこれで正しい」。やり取りはこの 2 つに合わせ、それ以外は問題が見つかったときだけ諮る。往復はユーザーの時間を使い、原文を作り直す代償はこちらの時間で済むため
- リポジトリ固有の慣行（版の番号の決め方、release PR の書式とマージの仕方、tag の形式、本文の言語と構成、外部の文書とその確認の仕組み、asset、通知先）は RELEASING.md が正。無ければ過去の release が慣行の現物で、そこから読み取れないことだけ尋ねる

## 入口

依頼の言い方ではなく、今の状態から始める箇所を決める。見るのは、RELEASING.md、release PR（番号、マージ済みか、CI、本文にある変更の一覧、コメント。文書の確認の仕組みが、確定すべき文書の注記をコメントで挙げていることがある）、前回の release とその tag、main の head と対象 commit が一致するか（release PR 以外の commit が main に入っていないか）、同じ tag の draft や tag が既にあるか、`.github/workflows` で main への push、`release` イベント、tag の push に反応するワークフロー、immutable releases の有無。

最初の応答では、状態、含まれる変更、本文の原文、判断を求める点をまとめて示す（下の Y1）。範囲の判断を要する問題（release PR に無い commit が main にある、CI が失敗している、既存の draft がある、RELEASING.md と状況が合わない）があれば、原文を書く前にそれを先に示す。原文は範囲の記述なので、範囲が決まらないうちに書くと書き直しになるため。

RELEASING.md が無く、慣行を過去の release から読み取って決めたときは、公開後の報告に、読み取った慣行を RELEASING.md に書く提案を添える。次の release で同じ読み取りを繰り返さないため。

## ユーザーとのやり取り

| 時点 | 示すもの | ユーザーの判断 | ここに置く理由 |
|---|---|---|---|
| Y1 最初の応答 | 状態。含まれる変更の一覧（本文に書くものと、書かないものとその理由）。版の番号とその根拠。latest にするか、prerelease か。release PR のマージ（main への push）と公開で起動するワークフローと通知。外部の文書の更新の案。本文の原文（日本語）と、取り決めがあれば下流の消費者への知らせの原文。これから行う書き込み（release PR のマージ、draft release の作成）。判断を求める点にはラベルを付ける | この範囲・この版で、この内容を言う（原文の校正）。挙げた書き込みに進んでよい | 範囲と原文は同じ判断の材料で、分けると往復が増える。範囲が違ったときの原文の作り直しは、こちらの時間で済む。マージで走るワークフロー（デプロイなど）は、マージの承認の材料になる |
| Y2 公開の承認 | 訳文の全文（最終言語が日本語なら省く。知らせの訳文も）と 3 辺の検査の結果。draft release の URL（描画された本文）。tag 名と指す SHA。latest と prerelease。起動するワークフロー。外部の文書に書き込む内容そのもの。承認の直後に、外部の文書の更新、publish、知らせの順に進むこと | 公開されるもの（本文、外部の文書、知らせ）はこれで正しい。進めてよい | 訳文の承認と公開の承認は、同じ対象（公開されるもの）への判断なので一つにする。描画された draft は、消費者が見るものに最も近い。外部の文書が本文の写しを持つなら、内容は訳の後でないと確定しない |
| Y3 公開後 | 公開された URL、tag が指す SHA、ワークフローの状態、外部の文書の反映、知らせを送ったこと | 要らない。異常があれば、事実と選択肢を添えて諮る | 判断が無いところで承認を求めない |

これ以外に諮るのは、範囲が release PR の記述や期待と合わないとき、校正で捉え方が変わって本文を書き直したとき（書き直した原文を再び校正に出す）、RELEASING.md と状況が合わないとき、公開後の確認で異常があったとき。

## 流れ

順序には理由があり、崩すとそれぞれに書いた失敗が起きる。

### 1. 範囲の確定（原文の前）

前回の release の tag から対象 commit までの変更を、マージされた PR の一覧（GitHub の自動生成の release note の API か、`git log`）で得て、release PR の本文の一覧と突き合わせる。release PR の本文は作成時点の意図で、現物はマージされた commit の側にあるため。

版の番号は、含まれる変更に照らして妥当かを確かめる（後方互換でない変更があるのに PATCH、など）。版は互換性についての主張で、本文の「要る対応」の記述と矛盾してはならないため。

### 2. 本文の原文（校正の前に訳さない）

[references/release-notes.md](references/release-notes.md) に従って日本語で書く。原文、範囲の一覧、対象 SHA、判断の記録は scratchpad のファイルに控える。会話が圧縮されても承認の対象を失わないため。訳は校正の後。先に訳すと校正が二度になる。

### 4. release PR のマージ（tag の前）

RELEASING.md の慣行に従う。tag はマージで main にできた commit を指すので、マージの前に tag は作れない。マージの後、main の CI が終わるのを待つ。公開は「この commit は使える」という合図で、CI が通っていない commit を配ると、読み手に通知だけが届くため。

### 5. 整合の準備（publish の前）

版の番号が現れる場所（tag 名、本文のタイトル、CHANGELOG、version を持つファイル、外部の文書）を列挙し、同じ版・同じ変更を指すようにする。version を持つファイルの更新は release PR に含まれているはずで、無ければ release PR の不備として諮る。外部の文書に書き込む内容はここで用意し、書き込みは Y2 の承認の後に行う。外部の文書が本文の写し（原文か訳文）を持つなら、同じ確定版から作る。

### 6. 訳と draft release

最終言語（過去の release の言語）に訳し、3 辺の検査（CLAUDE.md の出力スタイル節）を行う。下流の消費者への知らせの文面も、ここで訳す。draft release を、tag 名、対象 commit の SHA、タイトル、本文、prerelease で作る。GitHub の自動生成の節（PR の一覧と compare のリンク）を本文の後ろに付けるかは、過去の release の慣行に従う。target にはブランチ名でなく SHA を渡す。ブランチ名は publish の時点の head に解決され、draft の間に main が進むとずれるため。asset があれば draft に付ける（immutable では公開後に足せない）。

### 7. Y2、外部の文書、publish

承認の後、外部の文書を更新し、確認の仕組み（レビュー）があれば済ませてから publish する。公開で通知が飛び、読み手はすぐ見るため。publish の直前に、対象 SHA が範囲を確定したときから変わっていないか、draft の本文（自動生成の節を付けたなら、その前まで）が承認した文面と一致するか、対象 commit の CI が通っているかを確かめる。latest は publish のときに指定する（draft には設定できない）。

### 8. 公開後の確認、知らせ、Y3

[references/mechanics.md](references/mechanics.md) の確認を行う。下流の消費者への知らせは、release が公開されたことを確かめてから、承認した文面で送る。まだ見えない release を指す知らせを読ませないため。その後に報告する。公開後に誤りが見つかったら、直す前に、事実と選択肢（本文の編集、追加の release、取り下げ）を示す。本文の編集は通知されず、tag は動かせないので、どの選択にも代償があるため。

## 約束

- 取り消しにくい書き込み（release PR のマージ、tag、publish、外部の文書の公開、下流の消費者への知らせ）は、書き込む内容そのもの（文面、tag 名、SHA、フラグ）をユーザーが見て承認してから行う。承認の範囲が曖昧なとき（原文への承認が訳文を含むかなど）は、含まないものとして扱う
- publish の直前に、対象 SHA と draft の本文を確かめる（上の 7）
- GitHub の自動生成の release note を、本文の代わりにしない。PR のタイトルの列挙は、読み手の問いに答えないため。範囲の一覧と完全性の照合に使い、本文の後ろに付けるかは慣行に従う
- publish の後に本文を黙って直さず、tag を動かさない
