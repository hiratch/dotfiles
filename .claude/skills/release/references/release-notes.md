# release note

本文（release のタイトルと本文）の物差し、物差しから決まること、材料の集め方、慣行の扱い、校正と訳への出し方。

## 物差し

読み手は、利用者（振る舞い・画面・CLI を使う）、下流の消費者（API、スキーマ、出力の形式、設定に依存するコードやサービス）、運用する側（設定、環境、移行の手順）。どの読み手も問うのは次の 3 つで、本文をこれで測る。

- 自分に影響があるか
- 何をすべきか、いつまでに
- どこを見れば詳細が分かるか

物差しは 3 つ。

- 足りている: 各読み手がこの 3 つの問いに、diff や PR を読まずに答えられる
- 余分が無い: どの項目も、いずれかの読み手のいずれかの問いに答える。観察できる振る舞いを変えない変更（内部の整理、テスト、CI、開発にだけ使う依存の更新）は項目にせず、compare のリンクに任せる。ただし内部の整理は意図しない副作用を持ちうるので、振る舞いを変えない根拠（テスト、PR の Description の検証）を確かめ、確かでなければ項目にする
- 正しい: 各項目の主張が、対象の変更（PR、commit、diff）で成り立つ（3 辺の検査の①）。「要る対応」（後方互換でない変更、廃止、設定や環境の変更）は、PR の本文だけでなく差分で確かめる。PR の Description は作成者の意図で、release note は読み手に起きる観察のため

Keep a Changelog の「ほかに何もしないなら、廃止・削除・互換性を壊す変更だけは書け」と「commit の列挙は雑音」、Common Changelog の「各項目は見出しが無くても自立して読める」「互換性を壊す変更を先頭に」は、この物差しと同じことを言っている。

## 物差しから決まること

- 読み手が行動を決める順に置く。先頭は「要る対応」: 何が（機能名、API 名、設定名）、誰に（どの読み手に）、何をすべきか、いつまでに（廃止なら削除の予定）。次に振る舞いの変化（追加、変更、修正、削除、セキュリティ。見出しの語は慣行に合わせる）。最後に参照（前回の tag からの compare のリンク、各項目から PR へのリンク、この版に合わせて更新した外部の文書へのリンク。読み手が、文書がこの版に合っていると知れるため）
- 変化は、前と後の違いを観察の形で書く（「〜のとき〜が〜から〜になった」）。「改善した」「最適化した」「正しく動くようになった」のような解釈の語は、読み手が自分で影響を判定する材料を書き手の判定で置き換えるので使わない
- 読み手が使う語（機能名、エンドポイント、オプション、設定のキー）で書き、内部の名（モジュール名、ブランチ名、チケット番号だけの参照）で書かない。読み手は内部の名を自分の使い方に照らせないため
- 1 項目は 1 行を目安にし、長い説明は PR へのリンクに任せる。同じ機能に複数の PR があれば 1 項目にまとめ、打ち消し合う変更は書かない
- 版の番号と公開日は release のタイトルと tag と公開日時にあるので、本文で重ねない（慣行があれば従う）
- 版の番号は互換性の主張（semver なら、互換性を壊せば MAJOR、互換な追加は MINOR、互換な修正は PATCH。pre-release の識別子があれば prerelease）。本文の「要る対応」と矛盾していないかを確かめ、矛盾は Y1 で諮る

## 材料

- 範囲: 前回の release の tag から対象 commit まで。GitHub の自動生成の release note の API（mechanics.md）で、PR の一覧と compare のリンクを得る。`.github/release.yml` の除外（ラベルや作者）が効いて一覧から落ちる PR があるので、`git log <前回の tag>..<対象> --merges` か `gh pr list --state merged` でも突き合わせる
- 各 PR: タイトル、Description（課題、方針、範囲、検証）、ラベル。「要る対応」の判定に要れば diff
- 完全性: 一覧の各 PR を「本文に書いた（どの項目か）」「書かない（理由）」に分けて Y1 で示す。ユーザーが、落ちた変更が無いことを一覧で確かめられるため
- 慣行: 過去 2〜3 件の release の本文（言語、見出し、粒度、リンクの形、自動生成の節を残すか）。RELEASING.md があればそちらが正

## 校正への出し方

Y1 で出すのは、原文の全文と短い添え書き。添え書きには、他者向け文面の手順が求めるもの（3 辺の①を何で確かめたか）に加えて、範囲の一覧との対応（書いた・書かない）と、判断を求める点（ラベル付き。版の番号、latest と prerelease、書くか迷った項目、外部の文書の扱い）を書く。ユーザーが校正のときに、判断の材料を別に探さずに済むため。

校正で捉え方が変わったら、その文だけを継ぎ足さず、影響する項目を書き直す。継ぎ足すと、元の捉え方で組んだ文が残るため。書き直した原文は再び校正に出す。

## 訳

最終言語は、過去の release の言語（慣行が無ければ尋ねる）。訳の後に 3 辺の②と③を確かめ、訳文を draft release の本文にする。Y2 では、訳文の全文、どの辺を何で確かめたか、draft の URL を示す。描画の確認は URL で、承認の対象は訳文の全文で行えるようにするため。

外部の文書が本文の写しを持つとき（日本語の読み手向けに原文を置く、など）は、校正で確定した原文と、3 辺を確かめた訳文の、同じ確定版から作る。
