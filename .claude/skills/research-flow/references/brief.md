# 研究担当への依頼文の形

区切りの間ごとに 1 つ書き、並べるモデルに同じものを渡す。研究担当はこれと記録だけを読んで進めるので、会話でしか分からないことを残さない。メインの見立ては書かない。

```
# 研究担当への依頼: <テーマ>、区切りの間 <A〜D>（<日付>、<回>回目）

## この回ですること
- 段階: <段階の番号と名前。間 B なら 2 と 3>。段階ごとに、最初に Skill ツールで <スキル名> を呼び、それに従う
- 止まるところ: <この間の最後の段階> の記録の下書きができたところ。その先の段階へ進まない
- 入り直しなら: 変わった記録と箇所、その理由、確かめ直す記録（記録の形のファイルの「確かめ直し」に従う）
- 疑義の調べなら: 疑義（どの記録のどの項目か、いつ、何の観測から）と、確かめる現物。結果が記録の確定した事実と矛盾したら、それ以上進めずに、矛盾した観測を添えて返す
- D の 6 なら: 5 のまとめ（runs/D-<回>/5-merged.md）は相違を解いていない。相違ごとに推奨がどう変わるかを示す

## 読むもの
- 記録: <記録の置き場>/<テーマ>/ の state.md と、合意した記録 <ファイルの一覧>
- 記録の形: ~/.claude/skills/research-flow/references/records.md
- 読まないもの: 作業の置き場（~/tmp/research/<テーマ>/）のうちこの依頼文に挙げていないもの（他の回、他のモデルの出力、突き合わせ）。<5 より前なら: 控えたアイデアの場所は渡さない>
- <5 なら: 控えたアイデアの場所と、C3 でユーザーが述べたアイデア>

## 書くもの
- 書き出し先は依頼のメッセージで指定する（作業の置き場の runs/ の下）。その下以外に書かない
- 書き出し先に、段階の記録の下書き（記録の形のとおり）、返す報告と同じ内容の summary.md、実験をしたなら experiments/ を置く

## 使ってよい手間と環境
- <C1・C2 で合意した手間の目安、実験に使ってよいデータ・環境・時間。外部のサービスへの書き込みと、製品のコードの変更はしない>

## 返す報告（短く。全文は書き出し先に置く）
- 段階ごとの成果の要点（それぞれ 3〜5 行）
- 区切りでユーザーに決めてほしいことと、尋ねたいこと（ラベル付き）
- 合意済みの記録の不備を見つけたなら、その箇所と、戻るべき段階。見つけた時点で止めて返す（この回で書いた下書きの不備なら、その段階に戻って直して進める）
- 確かめられなかった範囲と、推定のまま置いた仮定
- 書いたファイルのパス

## 守ること
- <その研究に固有のこと（読まないファイル、公開のリポジトリに入りうる文面での組織固有の語の扱いなど）>
```

C1 で根が分かれたときの伏せた判定の依頼は、上の形を使わず、次だけを渡す。判定役が会話の文脈とメインの読みに引かれないようにするため。

```
# 根の判定の依頼: <テーマ>
- 読むもの: 下書き X と Y（モデルの名前を伏せた写し）、0-request.md、~/.claude/skills/research-problem/SKILL.md の「目的と終わりの状態」
- すること: どちらの根（解く問題と解けたと言える条件）が、示された根拠と達成条件に照らして確かかを、項目ごとに読む。どちらかに決めず、それぞれの強みと崩れどころを返す
- 書き出し先: <作業の置き場の comparisons/ の下>
```
