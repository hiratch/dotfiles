# 研究の記録の形と置き場

研究担当とメインが共有する。記録は、次の段階、入り直し、別のモデルや別のセッションの研究担当、開発担当への引き渡しの入力になる。会話を読まずに記録だけで続きが進められること、上から下へ矛盾なく読めることが、形の目的。

## 置き場

ユーザーと合意した記録を置く「記録の置き場」と、研究の途中の材料を置く「作業の置き場」を分ける。どちらも組織の案件の内容を含みうるので、公開の dotfiles には置かない。

記録の置き場は `~/.claude/reference/research.md` に書いてある（無ければユーザーに尋ねる）。版の管理があり、ユーザーが普段のノートの道具で読める場所にしてあるのは、戻ったときに記録の前の版と比べられ、区切りの 1 画面で足りないときにユーザーが全文を読めるため。commit と push はユーザーに任せる。

```
<記録の置き場>/<テーマ>/
  state.md            台帳: テーマ、依頼の一文、対象（リポジトリ・案件）、段階の状態の表、区切りの決定、作業の置き場と消す条件
  0-request.md        依頼（控えたアイデアを除く）と、始めに聞いたユーザーの答え
  1-problem.md, 2-requirements.md, 3-verification.md, 4-approaches.md, 5-user-ideas.md, 6-decision.md
                      合意した段階の記録
```

作業の置き場は、研究の途中の材料を置き、役目を終えたらメインが消す場所。

```
~/tmp/research/<テーマ>/
  runs/<間>-<回>/brief.md         その回の依頼文
  runs/<間>-<回>/<モデル>/         その回の下書き、summary.md、experiments/（実験のコードと結果。データそのものは置かず所在を書く）
  runs/D-<回>/5-merged.md         5 の 2 つの結果を、相違を解かずにまとめたもの（モデルの名前を伏せる。6 の入力）
  comparisons/<間>-<回>.md        メインの突き合わせ
~/tmp/research/log.md                  並べる試行の控え（研究をまたいで 1 区切り 1 行）
```

台帳の「作業の置き場と消す条件」には、このテーマの作業の置き場と、消す時点を書く。下書きと突き合わせは、研究を閉じるときにユーザーの OK の後。ユーザーの解決のアイデアを段階 5 まで控えているときは、「控えたアイデアあり（5 の記録を書いた直後に消す）」とだけ書き、場所は書かない（置き場は research-flow にある）。別のセッションで研究を閉じても、台帳を読めば何を消すかが分かるようにするため。

## 段階の記録の見出し

```
# <段階の名前>: <テーマ>
- 状態: 下書き | 合意済み | 要再確認（理由）
- 合意: <日時>、区切り <C1〜C4>
- 依拠した記録: <ファイル>（合意 <日時>）、…
```

記録が古いかは、見出しの「依拠した記録」に控えた合意の日時が、依拠した記録の今の合意の日時より前かで判断できる。前なら、上流が直された後にまだ導き直していない。入口で台帳の表と見出しを見て確かめる。

## 段階の記録の本文と末尾

本文の形は各段階のスキルの「出口」にある。本文で前提や事実を述べる項目には、確定（何で確かめたか）か、疑義（いつ、何の観測から生じたか）かを付ける。分かれていれば、どこまでが確かで、何を調べるべきかが記録から読め、確定した事実が簡便な調べもので黙って書き換わることを防げるため。

確定の根拠は、述べた内容そのものを確かめたものに限る。あることだけを確かめたもの（ファイルがある、など）は、中身（判定に足りる量と範囲か、など）については疑義とする。あることを中身の確定として扱うと、その上に積んだ段階が、確かめていない前提に依ることになるため。

末尾に次の 4 つを置く。

- 採らなかったもの: 検討して採らなかった候補・方向・要件と、採らなかった理由（どの基準・前提による判断か）。区切りでユーザーが選ばなかった側の案も入れる。前提が崩れて戻ったとき、最初に見直すべきなのは、その前提のおかげで退けた候補であることが多いため
- 未決: 判断、何で決まるか、誰が決めるか
- 根拠の所在: 出典（読んだ深さ: 本文、該当箇所、要旨、検索の要約、記憶）、実験、データ
- 変更の履歴: 日付、何を、なぜ、どの区切りで。疑義の解消（確定にした、取り下げた）も 1 行で残す

## 確かめ直し

上流の記録が変わった後に段階を走らせるときは、記録を一から作り直さない。変わった箇所がこの記録のどこに及ぶかを特定し、保つ部分には保つ理由を、直す部分は直して、変更の履歴に残す。一から作り直すと、変わっていない判断まで揺れて、ユーザーが合意済みの部分を読み直すことになるため。及ぶ範囲が記録の大半なら、作り直すと報告に書く。

## 依頼文なしで呼ばれたとき

研究担当のセッションでユーザーが段階のスキルを直接呼んだときは、どの研究か（記録の置き場の `*/state.md`）をユーザーに確かめ、依拠する記録が合意済みかを見てから始める。書き出し先は段階の記録そのもので、状態を下書きにして書き、ユーザーがそのセッションで合意したら合意済みにして台帳を更新する。

## 引き渡し

最後の区切りでユーザーが開発担当に引き渡すと決めたら、ユーザーと会話している側（メイン。研究担当を主にしたセッションなら、そのセッション）が、開発担当が作業するリポジトリの案件メモリに、`research-handoff-<テーマ>.md` として木の上の層を書き、MEMORY.md に入口の 1 行を足す。研究担当の実行は区切りの前に終わっていて、合意を持っているのは会話している側だから。書くのは、根となぜ今か、解けたと言える条件とその確かめ方（悪くしてはならないものを含む）、選んだ方針と退けた代替、方針が依拠する前提とそれが崩れたと分かる観測、未決の判断と何で決まるか、範囲外と調べて分かった落とし穴、マイルストーンと費やしてよい手間、記録の置き場のテーマのディレクトリ。開発担当はこれを根に契約を立て、前提の観測を止まる条件にする。方針だけを渡すと、開発担当は根を辿り直すか、方針を自分で書いた要件に照らして進めることになるため。研究は多くの場合、開発するリポジトリで行うので、そのセッションの案件メモリに書けばよい。研究を走らせたセッションが、開発担当の作業するリポジトリと違うときは、どこに書くかをユーザーに確かめる。

## 並べる試行の控え

`~/tmp/research/log.md` に、区切りごとに 1 行: 日付、テーマ、区切り、モデル、一致・相違・片方だけの数、土台にした側と他方から採った要素、相違がユーザーの判断を変えたか、片方のモデルだけが足した判断材料（どちらが、何を読んで）、ユーザーが全文を求めたか、決めるまでの問いの数、起動の確認ダイアログの回数とユーザーが負担に感じたか、入り直し（段階ときっかけ）、分かれば費用。並べる区切りの既定と、ダイアログの扱いを見直す材料にする。
