# レビュー返信への応答手順

返信は相手の発話への応答であって、指摘ではない。新規の指摘の書き方の決めごと（review-pr-topdown なら comments-and-posting.md、review-pr-steps なら SKILL.md の Step 6。配置先の選択・問題提起にとどめる・解決案を避ける・意図確認を避ける）は新規の指摘を起こすためのものなので、ここでは適用しない。

## 1. 相手の申告を裏取りする
コミットや修正が言及されている場合は、実際にその内容になっているかを確認する。申告をそのまま信用して返信しない。

修正が新しいロジック・構造を持ち込んでいる場合は、申告どおりかの確認に加えて、その部分を、使っているスキルの実現方法の観点（review-pr-topdown なら pr-judgment.md の「実現方法」、review-pr-steps なら pr-review-steps.md の Step 2〜5）で読む。ユーザーへの報告では、どの深さまで確かめたか（差分の読解・テストの実行・実データでの比較など）を明示する。

## 2. スレッドごとに相手の最後の発話を分類する
行レベルスレッドに加え、トップレベルコメントのやり取りも対象に含める。トップレベルは Resolve できないので、扱うのは返信のみ。
返信の形は「スレッドが着地したか」からは導けない。着地の判定は一様でも、応答すべき内容はスレッドごとに違う。文面に入る前に、各スレッドがどれかを明示する。

- **修正報告** — 直したという事実のみ。受理の一語で足りる
- **辞退・延期** — 直さない、または後続で扱うという判断。その判断を受け入れるかどうかを表明する
- **反論** — こちらの前提・事実認識の否定。訂正を受け入れるかどうかを表明する。受け入れる場合は指摘の根拠が覆ったことを認める
- **問いへの回答** — 指摘内で問うた点への答え。回答を受け取ったことを表明する
- **提案・打診** — 「〜してもよい」という形の申し出。同意するかどうかを表明する

1 つの返信が複数に該当することがある（例: 前提を否定しつつ代替案を出す）。その場合は両方に応答する。

## 3. 文面には自分の側にしかない情報だけを書く
書くのは、裏取りで自分が得た観測と、受け入れる／受け入れないの表明の 2 つだけ。相手が自分の返信に書いた commit SHA・修正内容・理由は言い換えない。相手はそれを知っている。

ユーザーへの検証報告をそのまま返信の材料にしない。報告は「何がどう変わったか」を伝えるものなので、流用すると相手の対応内容が混入する。返信は白紙から起こす。

文面ができたら、各文が「自分が測った値」か「受け入れる／受け入れないの表明」のどちらかであることを確認する。どちらでもない文は削る。相手の変更を主語にした文（「〜が〜になった」「〜を導入したことで〜」）はこの検査で落ちる。

## 4. 2 つの問いを分けて判断する
- 各スレッドに何を答える必要があるか（修正報告以外は一語で足りない）
- 新たな指摘を追加する必要があるか（通常は不要。手順 1 で修正が持ち込んだ部分に問題を見つけた場合など、必要な場合のみ、上の新規の指摘の書き方の決めごとに従う）

## 5. 返信文面と Resolve の可否をユーザーに確認する
行レベルスレッドとトップレベルのそれぞれについて、返信の要否を自分で判断し、必要と判断したものは文面を起こす。要否の判断結果と文面、および行レベルスレッドの Resolve の可否をまとめて確認に出す。承認後、返信を投稿してから Resolve する。返信せずに Resolve だけを行わない。

Approve に至りうる場合（指摘がすべて解消した、残件がなければ Approve と判定を委ねられる、など）は、この確認に Approve の判断材料を含める。残件なしとする基準と、最初のレビューから引き続き確かめていない範囲を示し、ユーザーがそれを見たうえで判断できるようにする。
