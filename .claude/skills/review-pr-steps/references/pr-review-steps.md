# PR レビューの観点と進め方（Step 1〜5）

レビューの目的は、PR のその時点の内容全体について、対応が必要か、その方針は妥当か、方針を正しく実現しているかを判断し、判断できない点や妥当でないと考える点に、根拠を添えて疑問を呈することにある。方向の誤りは細部の誤りより影響が大きく、見落とすと以降の確認がすべて誤った方針の上での確認になるので、必要性と方針（Step 1）を先に見て、実現方法（Step 2〜5）をレイヤごとに見る。各 Step の観点の一覧は見落としを防ぐためのものなので、どれも確かめる。

## 進め方
レビューは 2 周で進める。
- 1 周目（事前確認）では、ユーザーを待たずに Step 1〜5 の観点で PR 全体を確かめ、変更ファイルはすべて読む（元実装やリファレンスがあればそれも）。指摘は 2 周目まで出さない。通しで見れば解消する懸念を先に出さないためで、後の Step で解消した懸念は、解消した理由とともに控えておく
- 確かめる途中で情報が要っても止まらず、得られない前提で進め、要る情報は 2 周目の該当 Step で求める。PR を特定できないなど、確かめること自体が成り立たないときだけ、始める前に尋ねる
- 指摘・根拠・確かめられなかった範囲は、セッションの scratchpad にファイルとして控える。2 周目ではこのファイルを参照し、議論で変わった内容を反映する
- 2 周目（議論）では、Step 1 から順に、その Step の指摘を根拠とともに示し、ユーザーの質問や確認を待ってから次の Step へ進む。ユーザーが Step ごとに理解と合意を積み上げられるようにするため。指摘も示すもの（Step 1 の和訳、Step 2 の分類と解説など）も無い Step は、無いことを一文で述べて次へ進む。1 周目で解消した懸念は、指摘としてではなく、該当箇所の解説の中で理由を添えて述べる（「〇〇という意味なので問題ない」等）
- 議論の中で新たに確かめる必要が出たら、1 周目と同じ基準で確かめる

## 根拠の基準
- 必要性・方針への疑問（Step 1）は、根拠となるリポジトリの情報（Issue・文書・既存の設計）を示せるものに限る
- 実現方法の問題（Step 2〜5）は、対象のコードをそのまま動かして再現できる問題か、対象のコードが現に持っている性質に限る。改変したコードでの観測や、将来の変更を仮定した懸念は指摘にしない。依存先をスタブや monkeypatch で置き換えた観測も、改変したコードでの観測に当たる。とくに主張がその置き換えた部品の振る舞いに関わる場合、スタブは主張する振る舞いを組み込んでいるので、再現は循環して根拠にならない。部品の振る舞いについての主張は、本物の部品を動かした出力で示す
- いずれも、提示する前に根拠と深刻度を一文で言えることを確認する。言えないものは指摘にしない
- コードの仕組みを説明するときは、可能な限り実行して確かめてから述べる。測れない場合は、測っていないことを明示したうえで、説明ではなく確認事項として挙げる

## Step 1: 必要性と方針
問い: この PR が対処している課題は何か。なぜ解決する必要があるか。対処の方針は妥当で、より良い手段はないか。対処できたと言える根拠（検証の内容と結果）はあるか。これを、PR の課題そのものと、PR が課題を分解して立てた子課題のそれぞれについて問う。方向の誤りは細部の誤りより影響が大きく、子課題の立て方が誤っていると、子課題がそれぞれ正しく解かれていても元の課題は解けないため
- 課題の理解。Issue や Description の捉え方を前提にせず、実データや既存のコードで、何の現象・問題なのかを確かめる。捉え方がずれていると、正しく実装されていても別の問題を解いていることになるため
- 解決の必要性。リポジトリの開発方向性の中での PR の位置づけを、Issue、README や設計文書、最近の PR・コミット、リポジトリの CLAUDE.md、`~/.claude/reference` から把握し、なぜ今この課題を解く必要があるかを確かめる。分からない点は推測せず議論で尋ねる
- 方針の妥当性。ほかに取りうる方針を実際に挙げて比べ、目的をより本質的に満たすやり方があれば示す
- 対処できた根拠。検証の内容と結果が、その課題を実際に確かめているか（検証の対象や範囲が課題とずれていないか、結果が主張を支えるだけの量と質か）。Description の検証の記述だけでなく、diff のテストや実データでの確認と突き合わせる
- 子課題。PR が課題を分解して子課題を立てている（例: X を直すために、先に Y を変える必要があるとした）なら、その分解が妥当か（別の分解はないか）を確かめ、子課題ごとに上の 4 点を問う。実装の手順にすぎないもの（関数の分け方など）は子課題とせず、Step 2 以降で見る
- Description だけで必要性・方針・検証を判断できるか（書かれていなくても Issue 等で補えるなら可）。日本語以外で書かれていれば正確に和訳して示し、実装から補うときは「実装から推定」と明記する
- Description と diff の一致（記載漏れ・実装漏れ・記載と異なる実装）。diff に含まれる README・docs の記述（検証範囲・対象・数値など）とも突き合わせる

## Step 2: 実現方法 — ロジック
問い: ロジックは方針を正しく実現しているか。
- 元実装があれば、意図的な差異・省略
- 機械的な変更に紛れた実質的な変更。機械的と分類したファイルも全行を読む。整形やリネームの差分には、意味の変化が紛れても目立たないため
- 議論では、変更ファイルを本質的（ロジック・契約・データの流れが変わる）・機械的（整形やリネームの伝播など意味を変えない）・付随的（設定・依存・生成物の追随）に分けて示し、詳しく説明するファイルをユーザーと合意してから解説する。順序の指定が無ければ全体像から Top-Down に進め、大きなファイルは複数パートに分け、質問を受けてから次へ進む。ユーザーが全体像を掴んでから細部を見られるようにするため

## Step 3: 実現方法 — 可読性
問い: 読み手が、構造と命名から意図を読み取れるか。読み取れないコードは、後の変更で誤りを生むため。基準は開発担当の作法（可読性の優先、情報の置き場所、コメント・識別子の規範）
- 命名・構造・コメント、不要な複雑さや重複

## Step 4: 実現方法 — 実行時の挙動
問い: 本番の入力と環境で、正しく、十分な速さで動き続けるか。テストの通る入力だけでは、異常系・境界・既存データとの互換性の問題は表に出ないため
- 実行効率、異常系とエラー処理、入力の境界値、後方互換性（既存の呼び出し側・保存済みデータ・設定）

## Step 5: 実現方法 — diff の外への波及
問い: diff の外に、この変更に追随すべき箇所や、同じ問題が残っていないか。diff は変更の影響の全体ではないため
- 呼び出し元・呼び出し先の追随、同じパターンの問題が他の箇所に残っていないか、テストの追随、ドキュメント・設定・スキーマの追随
