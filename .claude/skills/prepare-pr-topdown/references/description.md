# Description

Description（タイトルと本文）の物差し、物差しから決まること、根拠の書き方、リポジトリの慣習の扱い、確かめ方、校正への出し方。

## 物差し

reviewer は、判断の核（`~/.claude/skills/review-pr-topdown/references/pr-judgment.md`）と同じ問いを PR に当てる。根と子課題ごとに、課題（何の現象・問題か）、必要性（解かないと誰が何に困るか、なぜこの PR で解くか）、方針（何を選び、なぜほかの方向ではないか）、根拠（何をどう確かめたか）を問い、そのうえで実現方法（方針が求める振る舞いを満たすか、変えたものを前提にする箇所が追随しているか）を判断する。Description を次の 2 つで測る。

- 足りている: reviewer がこれらの問いに、コードから意図を組み立て直さずに答えられる。実現方法の妥当性は reviewer がコードを読んで判断するので、Description が渡すのは、コードを照らす基準（変更の前後で振る舞いがどう変わるか、意図して扱わない入力や範囲）と、どこから読めばよいか
- 余分が無い: どの文も、いずれかの問いに答えている。答えない文は削る。diff を見れば分かる事実（変更したファイルの一覧、関数名の列挙、行数など）や、名前と構造から読める意図は、どの問いにも答えない

後の読み手は、なぜこの変更をしたかを Description から辿る。Issue や社内の文書へのリンクは後で読めなくなりうるので、課題と必要性は、リンク先を読まなくても本文で分かるように書く。

## 物差しから決まること

- 冒頭の数文で、何を変え、なぜかを言い切る。reviewer はまず課題と理由を掴んでから読み進めるため。タイトルは、PR の一覧や通知、リポジトリによってはリリースノートに単独で出るので、何をしたかがほかの PR と区別できる具体さで書く
- 課題の木に子課題があれば、節ごとに課題・方針・根拠を書く。小さな PR では根だけでよい
- 方針については、選ばなかった代替案のうち reviewer が問いそうなものとその理由、選んだ方針の代償（諦めたもの、既知の制約）を書く
- 範囲: 意図して扱わないことと、別の PR や Issue に回したもの（リンクと一言の理由）を書く。reviewer が欠けていると誤認しないため
- 関連する Issue へのリンクを書き、この PR で閉じる Issue は closing keyword（`Closes #番号` など）で結ぶ。マージで Issue が閉じ、後の読み手が Issue と PR を行き来できるため
- reviewer に判断してほしい点: self-review でユーザーが reviewer に委ねると決めた点を、選択肢と決め手とともに書く。reviewer の注意を、作成者が決めきれない箇所に向けるため
- stacked PR: どの PR の上に載り、どの順にマージする前提かと、draft のままレビューを依頼していること（base のマージの後に ready にする）を書く。reviewer が、レビューしてよい状態かで迷わないため
- 実装の細部はコードに任せ、Description では、どの変更がどの課題を実現しているかと、どこから読めばよいかを示すにとどめる

## 根拠の書き方

根拠は、reviewer が自分で判定できる形で書く。何を（主張）、何に対して（データ、環境、コミット）、どの基準で確かめ、何が観察されたかを書き、self-review で確かめられなかった範囲も書く。確かめていない範囲を、確かめたものと読ませないため。

- 手順は、reviewer に再現してもらうときに限り、そのまま実行できる深さで書く。そうでなければ書かず、何を確かめたかの一覧にとどめる。途中までの手順は実行できないうえ、検証のすべてに見えて、何がどこまで確かめられたかを読み違えさせるため。テンプレートの「How to confirm?」のような見出しにも、この基準で応じる
- 事実を述べる箇所では、観察そのもの（期待値の何と一致したか、何が何から何に変わったか）を書き、解釈の語（「正しく」「明らかに」「問題なく」「大幅に」など）で置き換えない。解釈の語は、reviewer が自分で判定するための材料を書き手の判定で置き換え、何を指すかが読み手によって分かれるため。書き手の判断を述べるときは、判断であることとその基準を示す
- 期待値を再生成したテストは、通ったことが根拠にならない（新しい出力に合わせて期待値を作ったため）。再生成した件数と、差分が意図した変化であることを何で確かめたかを書く
- 予期しなかった観察（意図しない差分、警告、前と違う結果など）があれば、それとその扱いを書く。reviewer が同じものに出会ったときに、既知かどうかを判断できるため
- チェックボックス（「pytest passed」など）も主張なので、ready にする head で確かめたものだけに印を付ける

## リポジトリの慣習

- PR のテンプレート（既定ブランチの `.github/`・ルート・`docs/` の `pull_request_template.md` か `PULL_REQUEST_TEMPLATE/` の下。無ければ組織の `.github` リポジトリの既定のもの）があれば、見出しの構造に従い、中身は物差しで決める。当てはまらない見出しは消さずに「なし」と書く。構造を保ちつつ、検討したことを示すため。作成者への指示（コメントや、置き換える前提の例文）は中身で置き換える
- テンプレートのコメントにリポジトリの決まり（インターフェイスを変えたら README も直す、など）があれば、PR がそれを満たすかを確かめ、満たしていなければユーザーに示す。テンプレートは、そのリポジトリが PR に求める条件の置き場所でもあるため
- テンプレートが無ければ、最近マージされた PR の Description を数件読み、言語・長さ・構造の慣習を掴む。慣習も無ければ、冒頭（何を変え、なぜか）、方針、根拠、範囲の順に置き、子課題があれば節に分ける。言語が慣習から決まらなければ、ユーザーに尋ねる

## 確かめ方

書き手は意図を知っているので、伝わらない文を伝わると判断しやすい。そこで日本語の原文ができたら、校正に出す前に、会話を見ていない開発担当のサブエージェントに読ませる（以下、下読み）。渡すのは、原文のファイル、PR の番号と判断した head の SHA、判断の核のファイルの場所だけとし、こちらの判断や経緯は渡さない。読み取りだけをさせ、次の 3 つを頼む。

- 判断の核の問いに根と子課題ごとに答え、答えごとに、Description から答えたか、コードから組み立て直したか、答えられなかったかを付ける
- どの問いにも使わなかった文を挙げる
- 現物と合わない記述を挙げる

組み立て直した答えと答えられなかった問いは、足すか、reviewer に問われてから答えれば足りると判断して残すかを決める。使われなかった文は削る候補にする。現物と合わない記述は、3 辺の検査の①の不成立として直す。

原文が長くなり、節が多くなるのは、PR が複数の課題を抱えている兆しなので、分けるかをユーザーに諮る。

## 校正への出し方

校正に出すのは、日本語の原文の全文と短い添え書き。添え書きには、他者向け文面の手順が求めるもの（どの辺を何で確かめたか）に加えて、次を書く。ユーザーが校正のときに、判断の材料を別に探さずに済むため。

- 下読みの結果をどう扱ったか（足したもの、問われてからで足りると判断して残した問い、削ったもの）
- 判断を求める点（あれば、ラベルを付けて）

校正で課題や方針の捉え方が変わったら、その文だけを継ぎ足さず、影響する節を書き直す。継ぎ足すと、元の捉え方で組んだ文が残るため。

確定の後に PR の内容が変わって書き直すときは、変わった部分と変わった理由を示して校正に出す。変わっていない部分も、今の head で成り立つかを確かめる。
