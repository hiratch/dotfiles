# review-session

## 目的と終わりの状態

セッションでの協働を振り返り、ユーザーが次の 2 つに使える材料を出す。主に、CLAUDE.md・担当の本文・スキル・hook・設定の変更（以下、指示の変更）。副に、ユーザーが、Claude への接し方（指示の出し方、問い方、指摘の仕方、判断の仕方）のより良いあり方を知ること。

振り返りは Claude の出来を採点するものではなく、協働の仕組み（読み込まれていた指示、モデルの傾向、ユーザーの入力、会話の状態）のどこを変えれば結果が変わったかを突き止める診断。指摘は成果物ではない。成果物は、置き場と文面が決まり、ユーザーが採る・直して採る・見送るを決められる変更の候補と、それを裏づける事象の引用。

終わったと言えるのは、候補のそれぞれに、事象の引用（記録の中の位置つき）、求めていたことの根拠、機構の見立て、既存の規則との照合、置き場と文面の案、削るもの、確かめ方が付き、候補がユーザーが一度に判断できる数に絞られ、候補にしなかった事象と議論の着地が 1 行ずつ示され、接し方の所見が候補と分けて示され、候補にユーザーが応えたとき。dotfiles 以外のセッションなら、合意した候補を dotfiles のセッションに渡す記録を書いたとき。

## 進め方の前提

- 指示を変えるときの作法は CLAUDE.md の協働スタイル節「CLAUDE.md・スキル・メモリに規則を足す前に」にあり、規則を足すのは最後の手段。失敗の多くは、当てはまる規則が既にあるのに効かなかったもので、直し方は、効かなかった理由（量に埋もれた、別の規則と矛盾した、文言が How で場面や目的が読めなかった）を直すこと。守られない行に強調を足しても過剰に適用されるだけで、曲げられない規則は hook に、埋もれる行は短くする。だから候補は、新しい規則より先に、既存の規則の直し・hook 化・削除の形で考える
- 規則は、制約より目的と動機の形のほうが汎化する。ユーザーの方針も「制約がなくても抵触しない動機付けや目的を与える」。候補の文面は、その目的を理解していれば他の制約が無くてもその場面で違う行動をしたと言える文にする。How の制約は、機械的に判定できるなら hook に、できないなら目的に言い換える
- 振り返りの最初の所見はたいてい不完全か間違っている。最初に浮かぶ教訓は「こうすべきだと思っていること」で、「実際に働くこと」ではない。モデルの出す改善案は、その状況に特化しやすい。だから候補は、このセッションに固有の事情を剥がして別の案件・別の担当でも当てはまるかを問い、確かめ方（次にどの場面で何を観察すれば効いたと言えるか）を付けてから出す
- 自分の行動を自分で振り返ると、正当化（根拠の薄い推論を事実のように述べる）と、ユーザーの見立てへの迎合の両方に引かれる。拠り所は会話の記録そのもので、見立てには、引用と、対立する見立てがなぜ退けられるかを添える
- 「Claude が規則を守らなかった」「ユーザーの指示が曖昧だった」は事象の記述であって原因ではない。原因は、その時点の文脈に何があり何が無かったか（規則は読み込まれていたか、当てはまると読める文言だったか、要る情報はどこにあり誰が知り得たか）にある。判断はその時点で持っていた情報で評価し、今の情報で何を変えるかとは分けて問う
- 圧縮の後の要約は Claude 自身の語り直しで、ユーザーの言葉そのものと訂正の前後の順序が落ちる。根拠は、ディスクに残る会話の全文の記録から取る。読み方は [references/transcript.md](references/transcript.md)

## 入口

依頼の言い方ではなく、今の状態から始める箇所を決める。見るのは、作業ディレクトリ（dotfiles か、ほかの案件か）、担当（なし・開発・研究）、圧縮が起きたか、記録の場所と大きさ、セッション中に使ったスキル、読み込まれていた指示（グローバルと案件の CLAUDE.md、担当の本文、使ったスキルの本文、settings の hook）。このセッションの ID は `${CLAUDE_SESSION_ID}`（スキルの読み込み時に置き換わる。置き換わっていなければ references の方法で探す）。

ユーザーが特定の場面を指して依頼したときは、その場面を中心にしつつ、同じ機構がほかの場面にも現れていないかを見る。1 件ずつ直すと、同じ原因の別の現れが残るため。

読み取りは許可を求めずに進め、最初の応答で候補まで示す。承認を求めるのは、会話を見ていない読み手のサブエージェントを使うときだけで、その承認は候補を示す応答に添える。

## 事象の集め方

事象とは、結果がユーザーの求めたものとずれた箇所、規則や約束が働いて結果を守った箇所、議論の着地、根拠の薄い判断や後の情報と整合しなかった判断。記録から、次を手がかりに拾う。

- ユーザーの訂正、問い直し、同じ指示の繰り返し、「〜ではないか」という問い、ツールの実行の拒否、中断。ユーザーの反応は「求めていたこと」の最も確かな根拠なので、事象には必ずその引用を付ける。同じ訂正が 2 回以上あれば、指示の変更の第一候補（Claude Code の文書は「2 回直したこと」を CLAUDE.md に書く条件に挙げる）
- Claude が述べた約束や計画と、その後の行動の食い違い。確かめずに確かめたと報告した箇所
- 反論や指摘の応酬の着地。Claude の立場、ユーザーの立場、双方を踏まえた新しい立場のどれに着地したかと、その過程が双方の納得できるものだったか。評価を述べずにユーザーの立場へ切り替えた箇所は、迎合の事象として候補の材料にする。ユーザーの問いが転換点になった箇所は、接し方の所見の材料にする
- 根拠が薄いまま結論に飛んだ箇所（双方の発言）と、後に出た情報と整合しなかったユーザーの判断（議論の進展による意図的な方向転換は除く）。Claude の側なら候補の材料、ユーザーの側なら接し方の所見の材料にする
- ユーザーが訂正しなかったが、読み込まれていた指示に照らしてずれている箇所。根拠が弱いので、候補にするなら「ユーザーの反応なし。こちらの見立て」と明示する
- 働いたもの。約束・規則・hook が失敗を防いだり迷いを無くしたりした箇所。規則を残す根拠になるので短く記録する（何を削るかを決めるときの材料）
- 費用。許可の確認、やり直し、往復の数が作業に見合わなかった箇所。置き場は設定（permissions・effort・hook）になる

事象ごとに、その時点の文脈に何があったかを確かめる。読み込まれていた指示のどれが当てはまるか、要る情報がその時点で会話にあったか、無ければ誰が知っていたか（ユーザーだけか、リポジトリにあったか、問えば分かったか）。見立ては、発言・ツールの呼び出し・その順序から立て、thinking のブロックは根拠に使わない（出力に写すと reasoning_extraction の拒否に触れうる。Fable 5 の指針）。

## 候補への絞り込みと判断

候補にする条件は 3 つ。指示・hook・ユーザーの入力のどれかを変えれば結果が変わったと言える（変えても変わらないものは候補にしない）。別のセッションでも起こりうる（この案件だけなら、案件のメモリへの記載の提案にとどめる）。害がある（ユーザーの時間、誤った成果物、取り消しにくい操作）。順位は、再発のしやすさ、害の大きさ、直せる確からしさで付ける。

事象ごとに機構を次のどれかに見立て、置き場を決める。この見立てが、CLAUDE.md の作法の問い（既存の規則で説明できるか、機械的に判定できるか、それでも足すなら何を削るか）に先回りして答える。

| 見立て | 置き場と形 |
|---|---|
| 当てはまる規則があったが効かなかった | その規則を直す。効かなかった理由を特定する。文言が How で目的が無く、当てはまる場面と読めなかった（目的を書き足す）。量に埋もれた（短くする、場所を変える）。別の規則と矛盾した（どちらかを消す）。場面の列挙に無かった（列挙でなく目的で書く） |
| 規則は無く、例外なく守るべきで、ツールの入力から機械的に判定できる | hook か permissions。判定する条件を書く |
| 規則は無く、判断を要する | 目的と動機の文を、CLAUDE.md（案件をまたぐ協働）・担当の本文（担当の作法）・スキル（その作業）のどれかに足す。同時に削るものを決める |
| 要る情報がその時点に無かった | 誰が知り得たかで分ける。Claude が問えたなら、問うべき場面を目的の形で書く候補。ユーザーだけが知っていたなら、接し方の所見 |
| 一回限り、またはモデルの傾向で指示では変わらない | 候補にしない。1 行で残す |
| 働いた | 残す根拠として記録 |

既存の規則との照合は、読み込まれていた指示のファイルを実際に検索し、当てはまる規則があればその文を引用し、無ければ探した場所を書く。記憶で「無い」と言わない。

候補の文面は、置き場が受け取る形で書く。規則なら目的と動機の文（組織固有の語を含めない。dotfiles は公開のため）。hook なら判定する条件。接し方なら、その場面でユーザーが足せた一文。文面を書いたら 2 つの問いを当てる。この目的を理解していれば、他の制約が無くてもその場面で違う行動をしたか。このセッションの事情を剥がしても意味が通るか。どちらかが否なら、文面を直すか候補から外す。

## ユーザーへの示し方

一度に判断できる量に絞る。詳しく示す候補は 3 件までを目安にし、残りの事象は 1 行ずつ（何が起き、なぜ候補にしなかったか）。議論の着地も、応酬ごとに 1 行（どの立場に着地したか、過程が双方の納得できるものだったか）で示す。候補 1 件は 10 行程度で、事象の引用、求めていたことの根拠、機構の見立てとその根拠の種類、既存の規則の照合、案（置き場・文面・削るもの）、確かめ方の順に書く。

接し方の所見は、候補と節を分け、判断を求めない。書くのは、効いた入力（どの言葉が何を変えたか）、足りなかった情報が後から出た箇所（その情報が先にあれば何が変わったか、ユーザーがその時点で知り得たか）、ユーザーの判断で根拠が薄かったか後の情報と整合しなかった箇所（その時点の情報で何ができたか、今の情報で何を変えるか）。「こうすべきだった」の形にしない。ユーザーの行動は規則にできず、知って選ぶのはユーザーのため。

判断を求める前に、記録からは検出できない種類の問題（双方が知らなかった前提、Claude の知識の盲点など）がありうることを、確かめられなかった範囲として一言添える。

末尾に、候補ごとにラベルを付けて判断を求める（採る・直して採る・見送る）。その上に推奨と理由。読む位置と根拠の書き分けは CLAUDE.md の出力スタイル節に従う。

## 突き合わせ

セッションが長い、圧縮が複数回あった、何が問題だったかについてユーザーと見解が分かれている、のいずれかなら、会話を見ていない読み手のサブエージェントに、記録の抜粋（thinking は除く）と読み込まれていた指示のファイルの場所だけを渡し、こちらの見立てを渡さずに、事象の一覧を独立に作らせて突き合わせる。自分の推論を見た読み手は同じ結論に寄るので、新しい文脈の読み手のほうが自己批評より当てになる（Fable 5 の指針、Claude Code の best practices）。ユーザーには差分だけを示す。

## 記録と引き継ぎ

dotfiles の変更は dotfiles のセッションで扱う。ほかのセッションからは、合意した候補を [references/handoff.md](references/handoff.md) の形で `~/tmp/session-review/` に書き、ユーザーにそのパスを示す。dotfiles のセッションは、それを読み、その時点のファイルに照らして反映し、反映の後に消す。記録には組織の内容（引用）が含まれるので、dotfiles には入れない。

dotfiles のセッションでの振り返りなら、引き継ぎの代わりに、候補をそのまま変更の提案として示す。適用はユーザーの判断の後で、CLAUDE.md の協働スタイル節の作法（Top-Down、書き込む内容そのものの提示）に従う。

途中の抜粋と下書きは scratchpad に置く。会話が圧縮されても候補と合意を失わないため。

## 崩さない順序

1. 記録を読んでから見立てる。要約や記憶から見立てると、Claude 自身の語り直しを根拠にすることになり、ユーザーの言葉と順序が失われる
2. 既存の規則と照合してから文面を書く。先に書くと、重複した規則を足す案になる
3. ユーザーの判断を得てから引き継ぎの記録を書く。先に書くと、dotfiles のセッションでユーザーが同じ判断を二度することになる

## 約束

- 振り返りの中で書き込むのは scratchpad と `~/tmp/session-review/` だけ。dotfiles を変えるのは、dotfiles のセッションで候補にユーザーが応えた後だけ。案件のメモリ、ほかの案件のファイルは変えない。規則を自分で足さない
- 引用は記録の文をそのまま写し、位置（記録のファイルと行、または時刻）を付ける。言い換えを引用の形で書かない
- 見立ての根拠の種類（記録の引用か、指示のファイルの読解か、推測か）を書き分ける。ユーザーの反応が無い事象は、その旨を明示する
- 引き継ぎの記録の「案」の欄に組織固有の語を書かない。「引用」の欄に含まれることは、記録が dotfiles に入らないことで許す
