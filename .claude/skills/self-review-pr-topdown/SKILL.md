# self-review-pr-topdown

## 目的と終わりの状態

reviewer が問うのと同じこと（対処している課題とその必要性、方針の妥当性、対処できた根拠、実現方法の妥当性）を reviewer に渡す前に判断し、答えられない点や妥当でない点を、直す・Description で説明する・Issue にする、のいずれかで解消する。

終わったと言えるのは、PR の内容全体について判断と根拠がそろい、合意した対応を終え、最終の状態でテストの全体を流し、self-review の記録を書いたとき。

## 進め方の前提

セルフレビューでも、律速はユーザーが判断を自分のものにするまでの負荷にある。PR はユーザーの名義で reviewer に渡るので、ユーザーは指摘とその対応に腹落ちしてから渡したい。他者の PR のレビューとは次の 3 点が違う。

- 自分の捉え方に引きずられやすい。課題の捉え方・方針・実装・Description は自分が作ったもので、意図を知っているために、読み手に伝わらない点や妥当でない点を妥当と判断しやすい。判断の核の「課題を現物で捉え直す」「方針の代替案を実装を読む前に立てる」も、自分だけでは守れない
- 懸念に当たらない点を詳しく示しても、ユーザーの判断の材料にならない。セルフレビューの後にユーザーが決めるのは、指摘への対応と、reviewer に渡してよいかで、後者に要るのは未解決の点と確かめられなかった範囲（見取り図と総括に載る）だから
- 作者は、reviewer の持たない記録（実装の入口で合わせた課題の木、案件メモリの引き継ぎ、前回のセルフレビューの未決、測った結果）を持っている。それを使えることが、セルフレビューが他者のレビューに勝る点で、判断の材料はまずそこにある。課題の木があれば、テスト・文書・Description が変更の約束（契約）と根の条件に追随しているかを照らす基準になる

## 判断の核

何を判断するか、候補を指摘にする条件、直し方、崩さない順序（上流と下流の意味を含む）、/code-review との分担は [references/pr-judgment.md](references/pr-judgment.md) にある。セルフレビューを始める前に読む。

自分の捉え方を補うため、会話の文脈を持たない開発担当のサブエージェントにも、判断の核に沿って PR を判断させる。開発担当にするのは、可読性の基準が開発担当の作法にあるため。渡すのは PR（またはブランチ）と判断の核のファイルの場所だけとし、こちらの判断や設計の経緯は渡さない。自分の判断と並行して背景で走らせ（前景で走らせると、続きの依頼に要るサブエージェントの ID が返らない）、自分が一巡した後に突き合わせ、食い違った点を候補に加える。判断の核が求める候補の反証は、同じサブエージェントに続けて依頼する。サブエージェントへの依頼にはユーザーの承認が要るので、セルフレビューを始めるときに、反証まで続けて依頼することを伝えて承認を求める。

## ユーザーへの示し方

最初に、PR 全体の見取り図を 1 画面程度で示す。

- Description が述べる課題と、現物で確かめた課題（違えばその違い）
- 課題の木: 節ごとに 1 行（課題、方針、根拠、判断）
- サブエージェントの判断と食い違った点
- 確かめられなかった範囲（実行できなかった検証、触れられなかったデータ）
- この後に示す順と件数

その後、指摘のある節を上流から示す。1 回に示すのは 1 つの節にまとまる指摘とし、多ければ（目安として 5 件を超えれば）重要なものから分ける。各指摘には、害と根拠の参照と確かさに加えて、対応の案（直す、Description で説明する、Issue にする、直さない）と推奨を添える。懸念に当たらない点は示さない。候補に挙がって解消したものは、指摘としてではなく、その節の中で解消した理由を一文で添える。ユーザーが同じ疑問を持ったときに確かめ直さずに済むため。

ユーザーの応答や修正で判断が変わったら、変わった項目を明示してから先へ進む。

## 対応

修正・Description の更新・Issue の起票は、ユーザーと合意したものだけを行う。

- 修正に合意した指摘は、その節のうちに直してコミットする。上流を直すと下流のコードが変わりうるので、下流は直した後のコードで示すため。コミットは、reviewer と後の読み手が変更を一文の主題ごとに辿る単位で、修正の置き場所もその読み方に合わせる
- Description の修正は、Description がまだ仮（ready にする前）なら、直す点として控え、Description を確定するときにまとめて校正する。校正を 1 回にするため。ready にした後の修正と Issue の文面は、グローバル CLAUDE.md の他者向け文面の手順に従う
- Issue にすると合意したものは、合意した時点で文面を下書きし、起票は総括で行う

## 総括

すべての節を示し終えたら、次を行う。

- 指摘ごとの対応（直した、Description で説明した、Issue にした、直さずに閉じた（その理由））の一覧と、確かめられなかった範囲・議論で詳しく扱わなかった範囲を示す
- Issue にすると合意したものを起票する
- 最終の状態でテストの全体を流し、結果を確かめる
- すべてコミットしてから、self-review の記録を書く: `~/.claude/hooks/pr-workflow-guard record --branch <レビューしたブランチ>`。記録するのはコミット済みの変更内容で、reviewer の指定と ready 化の前に、このガードが記録と照合する
