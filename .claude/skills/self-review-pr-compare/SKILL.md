# self-review-pr-compare

## 目的と終わりの状態

self-review-pr-topdown（以下 topdown）を主にしてセルフレビューを行い、self-review-pr-steps（以下 steps）の指摘を topdown の課題の木に統合して、漏れを補う。あわせて、steps だけが拾った指摘の数と、topdown がそれを落とした原因を、PR をまたいで記録する。原因は topdown を直す材料に、数は steps を退かせる判断の材料にする。強くするのは topdown の側だけで、steps は退かせるまで並走させて数える。

終わったと言えるのは、topdown の終わりの状態（合意した対応、テストの全体、self-review の記録）に達し、記録を書いたとき。reviewer の指定と ready 化はこのスキルでは行わず、PR を仕立てるスキル（prepare-pr-topdown か prepare-pr-steps）の後工程に任せる。

## 進め方

1. 始めるときに、このスキルが頼むサブエージェント（steps を走らせる開発担当）と、topdown が頼むサブエージェントを示し、承認を求める。
2. steps の事前確認を、背景の開発担当のサブエージェントに走らせる。渡すのは、PR（またはブランチ）、判断する head の SHA、steps の SKILL.md と手順書の場所、書き出し先だけで、topdown の判断は渡さない。1 周目（事前確認）だけを行い、修正・コミット・記録はせず、指摘の一覧を書き出させる（指摘ごとに、要旨・箇所・害・根拠・確かさ・推奨する対応。解消した候補と確かめられなかった範囲も）。コードは固定した SHA の git のオブジェクトで読ませる。topdown の修正で作業ツリーが途中で変わるため。返す報告は、書き出し先のパスと指摘の件数だけにさせ、指摘の要旨を含めさせない。報告はメインの会話に届くので、要旨が含まれると、topdown の判断を書き留める前にメインが読んでしまい、topdown が何を拾うかを測れなくなるため。
3. topdown の SKILL.md（`~/.claude/skills/self-review-pr-topdown/SKILL.md`）を読み、それに従って判断を進める。topdown の判断（課題の木、指摘の候補、解消した候補）を steps と同じ形で topdown.md に書き留めるまで、steps の一覧を読まない。先に読むと、木の上の層が steps の細部に引き寄せられ、topdown が何を拾うかを測れなくなるため。書き留めるのは、反証より前、ユーザーに示すより前に置く。topdown の総括（テストの全体と記録）は、5 の後に行う。
4. 書き留めたら、steps の一覧を読む。steps の指摘ごとに、同じ問題を指す topdown の指摘か解消した候補を名指しし、無ければ steps だけとして、対応の控え（mapping.txt）に書く。名指しは、メインが「topdown も拾っていた」と寄せて数える偏りを、後から確かめられるようにするため。そのうえで、steps だけの指摘と、一方が指摘にし他方が解消したもの（両方の理由を添える）を、topdown の反証の依頼（判断の核が求める、候補をまとめて 1 回で頼むもの）に入れる。判定役を置かないので、自分が拾えなかった指摘をメインが割り引いて見るおそれを、会話の文脈を持たないサブエージェントの確かめで抑えるため。
5. topdown の示し方に従い、steps の指摘を、それが属する課題の木の節に入れて、topdown の指摘と同じ形（害・根拠・対応の案と推奨）で示す。steps だけの指摘は、反証で成り立たないとしたものも、その理由を添えてすべて示す。成り立つかの最後の判断をユーザーに残すため。steps だけの指摘には、steps だけであることと、topdown がその候補をどう扱ったか（挙げなかった、解消した〔その理由〕）を 1 行添える。topdown が何を落としたかをユーザーがその場で見られ、記録に書く原因の分類を確かめられるため。合意した対応を行い、topdown の総括に進む。
6. 記録を書く。振り分けの結果に、ユーザーに尋ねた示し方の印象（分かりやすさ・負荷）を添え、まとめの記録に 1 行足す。漏れを観測した観点は所見として書き、スキルを直すかはユーザーが決める。あわせて、topdown が落とした指摘（steps だけのもの、ユーザーの問いから出たもの、反証やユーザーの判断で逆転したもの）ごとに、原因を、木の作り方（根の取りこぼし、根の高さ、根の経緯、どの根にも属さない変更、期待される変更の抜け）、節の確かめ方の深さ、行の単位、のどれかに分けて書く。木の作り方を変えた効き目と、行の単位を何が受け持つかを、記録で判断するため。あわせて、実装の段階の手当て（開発担当の入口の課題の木と、落ちるのを見てから足すテスト）が効いたかを見るため、次を書く。指摘の種類（文書の追随・テスト・挙動・可読性・設計）と出どころ（topdown のメイン、topdown のサブエージェント、steps、ユーザーの問い）ごとの数、課題の木が入口で作られたかと根の出どころ（辿った、案を示して直された、研究担当の引き渡し、根が無いまま進めた）、ユーザーが根・方針・決定の状態・分解を言い直した回数、後の段階が前の段階を作り直した回数、足したテストごとに落ちるのを見たか（変異か変更前のソースか）、設計の選択を開発担当が選択肢として示したかユーザーの問いから出たか（整合する形の重さを試作で測ったか）、止まる条件に当たった回数と止まったか、入口で増えた手間の概算。実装が別のセッションで記録の無いものは「不明」と書く。指摘の種類と出どころを数えられるのは一覧を突き合わせるこの場なので、その推移で手当てが効いたかを判断する。

## 数え方

steps を退かせる判断に使うのは、steps だけが拾って成り立ち、ユーザーが対応する（修正・Description での説明・Issue 化）と合意した指摘の数。成り立っても、ユーザーが対応しないとした指摘（害が小さいなど）は数えない。ユーザーとの議論で出た指摘は topdown の側に数える。退かせる判断は topdown とユーザーの協働で洗い出せているかで行うため。この数が直近 10 回続けて 0 になったら、steps を退かせることをユーザーに提案する。10 回続けて 0 なら、steps を並走させて補える漏れが topdown に残っていないと見なせるため。topdown だけが落とした指摘（steps だけのものと、ユーザーの問いから出たもの）は、topdown を直す材料として所見に書く。木の作り方と節の確かめ方の深さに起因する steps だけの指摘が 0 になった時点で、行の単位に残るものの受け持ち方（行の点検を戻すか、別の形にするか）を、記録を見てユーザーと決める。行の単位のものは木の判断から届きにくいことがあり、届くかどうかを記録で確かめてから決めるため。

## 記録の場所

組織のリポジトリの中身を含むので、公開の dotfiles には置かない。

- PR ごと: `~/tmp/selfreview-compare/<リポジトリのディレクトリ名>-pr-<番号>/`（PR が無ければ番号の代わりにブランチ名）。steps.md、topdown.md（steps を読む前に書き留めた topdown の判断）、mapping.txt（振り分けの名指し、出どころ、反証の結果、ユーザーの判断）を置く
- まとめ: `~/tmp/selfreview-compare/log.md` に、PR ごとに 1 行（日付、PR、両方・topdown の側だけ・steps だけの成り立つ指摘の数、steps だけのうち対応すると合意した数、ユーザーの問いから出た指摘の数、topdown が落とした指摘の原因ごとの数（木の作り方・節の確かめ方の深さ・行の単位）、示し方の印象、時間の内訳、所見）。時間の内訳は、記録を書く直前に `~/.claude/skills/self-review-pr-compare/scripts/review-time self-review-pr-compare` の出力をそのまま写す（「不明」と出たらそれを写す）。承認の待ち、ユーザーの思考の時間と往復の数、待ちの後の思考の時間を、手当ての前後で同じ物差しで比べるため。実装の段階の手当ての欄は、同じファイルの別の表に PR ごとに 1 行（指摘の種類ごとの数、課題の木の有無と根の出どころ、言い直しの回数、段階の作り直しの回数、落ちるのを見たテストの数と足したテストの数、設計の選択の出どころ、止まる条件に当たった数と止まった数、手間の概算）

## 約束

- steps のサブエージェントには、読み取りだけをさせる（編集・コミット・PR への書き込みをしない）
- topdown の約束（修正は合意したものだけ、他者向けの文面の手順、記録はすべてコミットしてから）はそのまま守る
