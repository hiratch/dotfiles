# PR レビュー共通手順（Step 1〜5）

レビューは 2 段階で進める。まず事前確認として、ユーザーを待たずに Step 1〜5 の観点で PR 全体を一人で確認する。その後、議論として Step 1 から順に、確認で得た指摘をユーザーに提示し、理解と合意を積み上げる。

## 前提
- PRのDescriptionを確認してください（スクリーンショットやURLが提供される場合あり）
- 引数として PR 番号が渡された場合は `gh pr view <番号>` と `gh pr diff <番号>` で Description と diff を取得してください。渡されなかった場合は現在のブランチに紐づく PR を解決してください
- 元実装やリファレンスがある場合はそれも参照してください
- 指摘として挙げてよいのは、対象のコードをそのまま動かして再現できる問題か、対象のコードが現に持っている性質に限る。改変したコードでの観測や、将来の変更を仮定した懸念は指摘にしない。提示する前に、再現する入力と生じる結果、および深刻度を一文で言えることを確認する。言えないものは指摘にしない

## 事前確認
- ユーザーの確認を待たずに Step 1〜5 の観点をすべて確認する。途中の結果も、終わったときの要約も提示しない
- 変更ファイルはすべて読む
- 情報が必要になっても止まらず、得られない前提で確認を進め、必要な情報は議論の該当 Step で求める。PR を特定できないなど、確認そのものが成り立たない場合に限り、開始前に尋ねる
- コードを実行して確かめるときは、ユーザーの作業ツリーのブランチを切り替えない。PR のブランチが checkout されていなければ、別の worktree を作って実行する
- 指摘・根拠・確かめられなかった範囲を、セッションの scratchpad にファイルとして記録する。後段の Step で解消された懸念は指摘にせず、解消した理由とともに別に記録する。議論ではこのファイルを参照し、議論で変わった内容を反映する

## 議論
- Step 1 から順に、その Step の指摘を根拠とともに提示し、ユーザーの質問や確認を待ってから次の Step に進む
- 指摘の無い Step は、指摘が無いことを一文で述べて、そのまま次の Step に進む
- 事前確認で解消した懸念は、該当箇所の解説の中で理由を添えて述べる（「〇〇という意味なので問題ない」等）。指摘としては扱わない
- 議論の中で新たに確かめる必要が出たら、事前確認と同じ要領で実行して確かめる
- 作成した worktree は Step 6 の後に削除する

## Step 1: Description vs 実装の乖離チェック
- PRのDescriptionが日本語以外で書かれていた場合、正確に和訳して提示してください。必要に応じて実装から読み取れることを補足してくれると嬉しいですが、その際は（実装から推定）などわかるように書いてください。
- このDescrption自体をレビューしてほしいです。
  - PRの目的、手段、検証方法について
    - 明記されているか。されていないならば、それが必要ないほど簡単か。あるいはIssue等を参照すれば確認可能か？
    - 論理的に明快か。可読性に問題がないか
    - 一貫性があるか（矛盾がないか）。リーズナブルな内容になっているか
- PRのDescriptionに記載された変更内容と、実際のdiffを比較
- 記載漏れ、実装漏れ、記載と異なる実装があれば指摘

## Step 2: 変更ファイルの解説とロジックレビュー
- まず全変更ファイルを一覧し、各ファイルを1〜2行で変更の性質に分類する
  - 本質的な変更: ロジック・契約・データの流れが変わるもの
  - 機械的・定型的な変更: フォーマッタによる整形、識別子リネームの伝播、import の並べ替えなど、意味を変えないもの
  - 付随的な変更: 上記に伴う設定・依存・生成物の更新
- 機械的と分類したファイルも全行を読み、意味を変える変更が混ざっていないかを確認する。整形差分に紛れた実質的な変更は見落とされやすい
- 各ファイルについてロジックに破綻がないか確認する。元実装がある場合は意図的な差異・省略がないかも確認する
- コードの仕組みを説明するときは、可能な限り実行して確かめてから述べる。コードを読んだだけで理解したつもりにならない。測れない場合は、測っていないことを明示したうえで、説明ではなく確認事項として挙げる
- 議論では、分類を提示し、詳しく説明するファイルをユーザーと合意したうえで解説する（ユーザーが順序を指定した場合はそれに従う。そうでなければ全体像から理解するためにTop-Downに行う）
  - 変更点が大きな場合は、1ファイルを複数パートに分けて説明する
  - ユーザーの質問を受け付けてから次のファイルあるいはパートに進む
- 議論で詳しく扱わなかったファイルは Step 6 で明示する

## Step 3: 可読性レビュー
- 命名、構造、コメントの適切さ
- 不要な複雑さや重複がないか

## Step 4: 実行時の挙動レビュー
- 実行効率: メモリ使用量、不要なデータコピー、パフォーマンス上の懸念点
- 異常系とエラー処理: 失敗時の挙動、リソースの解放、エラーを握り潰していないか
- 入力の想定範囲と境界値: 空・ゼロ・最大・想定外の型や順序で破綻しないか
- 後方互換性: 既存の呼び出し側、保存済みデータ、設定への影響

## Step 5: diff の外の確認
- 変更された関数・クラスの呼び出し元と呼び出し先を確認し、追随が必要なまま残っている箇所がないか見る
- 同じパターン・同じ問題が他の箇所にも存在しないか確認する（今回直した不具合が別の場所に残っていないか）
- テストの追随を確認する。変更に対応するテストがあるか、変更によって前提が崩れる既存テストがないか
- ドキュメント・設定・スキーマなど、コード外で追随が必要なものがないか確認する
- 確認した範囲と確認していない範囲を明示する。網羅したと誤認させない
