# PR レビュー共通手順（Step 1〜5）

レビューは 2 段階で進める。まず事前確認として、ユーザーを待たずに Step 1〜5 の観点で PR 全体を一人で確認する。その後、議論として Step 1 から順に、確認で得た指摘をユーザーに提示し、理解と合意を積み上げる。Step 1 は PR の必要性と方針を、Step 2〜5 は実現方法の妥当性をレイヤごとに見る。

## 入力
- Description と diff。PR 番号が渡されれば `gh pr view <番号>` と `gh pr diff <番号>` で、渡されなければ現在のブランチに紐づく PR から取得する。Description は URL やスクリーンショットで渡されることもある
- 元実装やリファレンスがあればそれも参照する

## 根拠の基準
- 必要性・方針への疑問（Step 1）は、根拠となるリポジトリの情報（Issue・文書・既存の設計）を示せるものに限る
- 実現方法の問題（Step 2〜5）は、対象のコードをそのまま動かして再現できる問題か、対象のコードが現に持っている性質に限る。改変したコードでの観測や、将来の変更を仮定した懸念は指摘にしない
- いずれも、提示する前に根拠と深刻度を一文で言えることを確認する。言えないものは指摘にしない
- コードの仕組みを説明するときは、可能な限り実行して確かめてから述べる。測れない場合は、測っていないことを明示したうえで、説明ではなく確認事項として挙げる

## 事前確認
- ユーザーの確認を待たずに Step 1〜5 の観点をすべて確認する。途中の結果も、終わったときの要約も提示しない
- 変更ファイルはすべて読む
- 情報が必要になっても止まらず、得られない前提で確認を進め、必要な情報は議論の該当 Step で求める。PR を特定できないなど、確認そのものが成り立たない場合に限り、開始前に尋ねる
- コードを実行して確かめるときは、ユーザーの作業ツリーのブランチを切り替えない。PR のブランチが checkout されていなければ、別の worktree を作って実行する
- 指摘・根拠・確かめられなかった範囲を、セッションの scratchpad にファイルとして記録する。後段の Step で解消された懸念は指摘にせず、解消した理由とともに別に記録する。議論ではこのファイルを参照し、議論で変わった内容を反映する

## 議論
- Step 1 から順に、その Step の指摘を根拠とともに提示し、ユーザーの質問や確認を待ってから次の Step に進む
- 指摘が無く、ほかに提示するもの（Step 1 の和訳、Step 2 の分類と解説など）も無い Step は、指摘が無いことを一文で述べて、そのまま次の Step に進む
- 事前確認で解消した懸念は、該当箇所の解説の中で理由を添えて述べる（「〇〇という意味なので問題ない」等）。指摘としては扱わない
- Step 2 では、変更ファイルを本質的（ロジック・契約・データの流れが変わる）・機械的（整形やリネームの伝播など意味を変えない）・付随的（設定・依存・生成物の追随）に分類して示し、詳しく説明するファイルをユーザーと合意してから解説する。順序の指定が無ければ全体像から Top-Down に進め、大きなファイルは複数パートに分け、質問を受けてから次へ進む
- 議論の中で新たに確かめる必要が出たら、事前確認と同じ要領で実行して確かめる
- 作成した worktree は Step 6 の後に削除する

## Step 1: 必要性と方針
- リポジトリの開発方向性の中での PR の位置づけ。Issue、README や設計文書、最近の PR・コミット、リポジトリの CLAUDE.md、`~/.claude/reference` から把握し、分からない点は推測せず議論で尋ねる
- 対応の必要性と、方針の妥当性（ほかに取りうる方針と比べて）
- Description だけで必要性・方針・検証を判断できるか（書かれていなくても Issue 等で補えるなら可）。日本語以外で書かれていれば正確に和訳して示し、実装から補うときは「実装から推定」と明記する
- Description と diff の一致（記載漏れ・実装漏れ・記載と異なる実装）

## Step 2: 実現方法 — ロジック
- ロジックが方針を正しく実現しているか。元実装があれば、意図的な差異・省略
- 機械的な変更に紛れた実質的な変更（機械的と分類したファイルも全行を読む）

## Step 3: 実現方法 — 可読性
- 命名・構造・コメント、不要な複雑さや重複

## Step 4: 実現方法 — 実行時の挙動
- 実行効率、異常系とエラー処理、入力の境界値、後方互換性（既存の呼び出し側・保存済みデータ・設定）

## Step 5: 実現方法 — diff の外への波及
- 呼び出し元・呼び出し先の追随、同じパターンの問題が他の箇所に残っていないか、テストの追随、ドキュメント・設定・スキーマの追随
