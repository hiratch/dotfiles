# review-pr-topdown

## 目的と終わりの状態

PR のその時点の内容全体について、対処している課題とその必要性、方針の妥当性、対処できた根拠（検証の内容と結果）、実現方法の妥当性を判断し、判断できない点や妥当でないと考える点に根拠を添えて疑問を呈する。

終わったと言えるのは、PR の内容全体について判断（または疑問）と根拠がそろい、確かめられなかった範囲が示され、投稿するコメントの配置先・文面・レビューの種類にユーザーが合意したとき。投稿はその後、末尾の約束に従って行う。

## 進め方の前提

レビューの律速は、モデルが読む量ではなく、ユーザーが判断を自分のものにするまでの負荷にある。コメントはユーザーの名義で出るので、ユーザーは PR の中身と判断に腹落ちしてから出したい。一度に受け取れる量には限りがあり、後で取り下げる指摘はその限られた注意を無駄にする。そこで、判断はモデルの側で確定させてから、上流から少しずつ、ユーザー自身が確かめられる参照を添えて示す。

## 判断の核

何を判断するか、候補を指摘にする条件、直し方、崩さない順序（上流と下流の意味を含む）、/code-review との分担は [references/pr-judgment.md](references/pr-judgment.md) にある。レビューを始める前に読む。

## 入口

前に判断した状態がある場合（投稿済みのレビューがある、PR が更新された）は、ユーザーが前に判断した状態と今の PR との差を見る。ユーザーが投稿したレビューがあれば、その commit_id とスレッドを起点に、以後のコミット・force push・タイトルや説明の変更・返信を見る。差の中身から、どこまで見直すか（最初からか、根拠が変わった判断だけか）を判断してユーザーに諮る。返信ごとに懸念が解消したかを根拠つきで判断し、追加の変更にも同じ条件を当てる。返信への応じ方は [references/reply-to-review-replies.md](references/reply-to-review-replies.md) にあり、相手の反応に応じるたびに読み直す（記憶で運用して作法を外したことがあるため）。返信や修正があるという入口の形で範囲を決めると、作り直された PR を古い判断のまま扱ってしまうため

## ユーザーへの示し方

最初に、PR 全体の見取り図を 1 画面程度で示す。

- PR が解くと言う課題と、現物で確かめた課題（違えばその違い）
- 課題の木: 節ごとに 1 行（課題、方針、根拠、判断）
- この PR の妥当性が主に懸かっている点。ユーザーが重点を指定していればそれを使う
- 確かめられなかった範囲（実行できなかった検証、触れられなかったデータ、説明の記述だけに依った判断）
- この後に示す順と件数

その後、上流から節ごとに示す。1 回に示すのは 1 つの節にまとまる判断とし、多ければ（目安として 5 件を超えれば）重要なものから分ける。各判断には害と根拠の参照と確かさを添え、ユーザー自身が見ておけば判断に責任を持てる箇所を 1〜2 か所挙げる。指摘の無い節も、何をどこまで確かめて妥当としたかを示す。Approve の根拠になるため。

ユーザーの応答で判断が変わったら、変わった項目を明示してから先へ進む。

## 文面と投稿

コメントの配置先と文面、レビューの種類の決め方、投稿の手順は [references/comments-and-posting.md](references/comments-and-posting.md) にある。文面に取りかかるときに読む。

次の約束は例外なく守る。

- 投稿・Approve など PR に書き込む操作は、ユーザーの承認を得てから行う。行う直前に、PR の head が判断したときの SHA から変わっていないかを確かめる。変わっていたら書き込まず、差分を見て影響する判断と文面を見直し、ユーザーに示し直す
- 他者に出す文面は、グローバル CLAUDE.md の他者向け文面の手順に従い、3 辺の検査を行ってから提示する
- 回答や対応次第で修正が入りうるコメントを含むレビューは Comment で出す。Approve は、残るコメントがいずれも修正を求めない場合に限る。Approve するときも、判定を伝える一言を添える
