# PR の判断の核

他者の PR のレビューと、自分の PR のセルフレビューに共通する、何を判断し、何を指摘にし、どう直し、どの順序を崩さないか、組み込みの /code-review とどう分担するか。ここで上流とは課題・必要性・方針の判断を、下流とは実現方法の判断を指す。

## 何を判断するか

PR が述べること（説明、コミットメッセージ、コメント。リファクタリングで振る舞いを変えないといった暗黙の主張を含む）は主張として扱い、その基準となる現物（生のデータ、リポジトリの開発の方向、元の実装、リファレンスや合意した構想、仕様）と突き合わせて判断する。PR を PR 自身と照らしても、基準からのずれは見えないため。答えられないときは「判断できない」とし、何があれば判断できるかを書く。

### 課題とその分解

PR の課題を根とし、PR がそれを分解して立てた子課題を枝とする木（以下、課題の木）を、PR の説明・Issue・コミット・コードから組み立てる。子課題とは、それ自体に「なぜ要るか」と「解けたと言える条件」を問えるもの（原因の特定、既存データの移行、互換性の維持など）を指す。関数の分割やファイルの移動のような実装の手順は、方針を実現する手段なので子課題にしない。PR が分解を明示していなければコードから読み取り、読み取りであることを示す。小さな PR では木は根だけでよい。

PR の説明（Description）は、日本語以外で書かれていれば正確に和訳して示す。ユーザーが原文の主張を自分で確かめられるようにするため。説明に書かれていないことを実装から補うときは「実装から推定」と示す。説明・diff・diff に含まれるドキュメントの記述（検証の範囲・対象・数値など）が食い違っていないかも確かめる。

木の根と各子課題で、次を判断する。いずれも判断の問いであり、項目を埋めることが目的ではない。

- 課題: 何の現象・問題か。生のデータ（ログ、再現、実データ、コードの経路）で現象そのものを確かめる。説明の捉え方を前提に影響を論じると、実際には別の現象だったときに気づけないため。説明と現物が食い違えば、それが最も上流の判断になる
- 必要性: 解かないと誰が何に困るか。いまこの PR で解く理由があるか
- 方針: 方向の違う代替案を自分で立てて比べたうえで、PR の方針が妥当か。代替案には、別の層で解く、既存の仕組みに乗る、範囲を絞る、解かない、を検討に含める。比べる基準は、その課題で何を優先すべきかから決める（PR が示していればそれを使い、無ければ自分の推定であることを示す）
- 根拠: PR が示す検証が、主張そのものを確かめているか。代理の指標や中間状態を見ていないか。主張が崩れても通る検証は、主張の根拠にならないため。手元で再実行・再現できるものは自分で確かめる
- 分解の妥当性（子課題を持つ節のみ）: 子課題の集合で親の課題が解けるか。欠けている子課題、要らない子課題、境界のずれがないか

### 実現方法

変更されたもの（コード、テスト、設定、ドキュメントなど）について、次を判断する。判断は、その変更が実現している課題の木の節に結び付ける。示すときのまとまりになるため。

- ロジック: 方針が求める振る舞いを、到達しうる入力と状態のすべてで満たすか
- 機械的な変更に紛れた意味の変化: 整形やリネームの伝播のように機械的に見えるファイルも、全行を読む。意味の変化が紛れても目立たないため
- 可読性: 読み手が構造と命名から意図を復元できるか（基準は開発担当の作法の可読性の項）
- 実行時の挙動: 実際のデータ量のもとでの処理時間とメモリ消費、並行性、失敗（例外、再試行、部分的な失敗）のもとでどう振る舞うか。テストの小さな入力では、これらの問題は表に出ないため
- diff の外への波及: 変えたものを呼ぶ・読む・前提にする箇所（呼び出し元、設定、データの利用者、他のリポジトリ）と、変えたものと同じ判断を持つ箇所（同じパターンのコード、テスト、ドキュメントやコメント）が、変更に追随しているか。既存の呼び出し側・保存済みのデータ・設定との互換性を含む。一か所だけを変えると、残った箇所との食い違いが別の問題になるため

## 候補を指摘にする条件

次をすべて満たしたものだけを、指摘としてユーザーに示す。満たさないものは示さないか、確かめられなかった範囲に入れる。

- 害が言える: 誰が（利用者、運用者、呼び出し元、将来の読み手など）、どの条件で、何に困るかを具体的に言える。害は、対象のコードがそのまま持っている性質として言えるものに限る。コードを改変して観測した害（依存先をスタブで置き換えた観測を含む）や、将来の変更を仮定した害は含めない。表面の差（文書の一文の変化、警告の有無など）は、それだけでは害ではない
- 根拠がある: ユーザーが開いて確かめられる参照がある。コードは判断した head の SHA でのパスと行で示し、実行したものはコマンドと結果を、データや文献は所在を示す
- 反証を経ている: すべての観点を一巡した後に、他の箇所・他の観点・PR の説明・既存のテストによって解消しないかを確かめた。修正を求める候補は、会話の文脈を持たないサブエージェントにも反証を試みさせる。こちらの捉え方に引きずられずに確かめられるため。サブエージェントへの依頼にはユーザーの承認が要るので、候補をまとめて 1 回で依頼する。指摘の害と根拠の文は、ユーザーがそのまま判断に使い、文面にして自分の名義で出す。反証は、指摘が成り立つかだけでなく、その文が名義に耐えるかを確かめるためにある
- 上流と整合している: 上流の判断の答え次第で意味を失う指摘は、上流が決まるまで保留する。上流の答えに関わらず成り立つ指摘は保留しない

指摘に値するかと、この PR で扱うべきか（別の PR や Issue に回すべきか）は分けて判断し、どちらも自分の判断を示してユーザーに確認する。

問いの形にするのは、コードやデータから自分で答えを出せず、かつ答えによって結論（修正の要否や方向）が変わるときに限る。答えの候補ごとに何が変わるかを添える。答えても何も変わらない問いは、往復を増やすだけなので出さない。

## 直し方

直し方（レビューでは指摘で示す修正の方向、セルフレビューでは実際の修正）は、採られればそれが次の変更になる。そこで、PR の変更に向けるのと同じ問いで判断する。とくに、直したい振る舞いが、問題の通る経路のすべてで満たされるか（ロジック）、直ったことの確かめ方が、直っていなければ落ちるか（根拠）を問う。直し方を決めるときと、議論で判断を変えるときは、上流と下流それぞれへの影響も確かめる。整合しないままその箇所だけを変えると、別の問題を引き起こすため。

## 崩さない順序

手順は状況に合わせて組んでよいが、次の順序は崩さない。崩すと、それぞれに書いた失敗が起きる。

1. 課題を現物で捉え直してから、方針と影響を論じる（理由は「課題」の項）
2. 方針の代替案は、PR の実装を細部まで読む前に立てる。読んだ後に立てると、PR の実装の変形しか出てきにくいため
3. 課題の木と実現方法をすべて一巡して候補を確定してから、ユーザーに示し始める。一巡する前に示すと、別の観点で解消する指摘を出してしまうため。ただし、分析を進められなくなる前提の不明点（ドメインの意図、触れられないデータなど）は先に訊いてよい。一巡した結果（判断、根拠、確かめられなかった範囲、解消した候補とその理由）はセッションの scratchpad のファイルに控え、示すときに参照し、議論で変わったら更新する。長いレビューで会話が圧縮されても、確認の結果を失わないため
4. ユーザーには上流から示し、下流は後にする。上流の判断で下流の指摘の意味が変わるため

## /code-review との分担

組み込みの `/code-review` は、diff の正しさの不具合を、会話の文脈を持たない別のサブエージェントで探す。ロジックの変更が多い PR では、最初に背景で走らせてよい。対象は、レビューでは PR 番号、セルフレビューでは今のブランチ（引数なし）とする。結果は、自分の上流の判断を固めた後に候補として取り込み、ほかの候補と同じ条件で指摘にするかを決める。上流の判断より先に取り込むと、注意が実装の細部に寄るため。`--comment` と `--fix` は付けない。前者はユーザーの承認を経ずに投稿し、後者はユーザーとの合意を経ずに作業ツリーを書き換えるため。課題の木の判断と、可読性・実行時の挙動・波及の判断は、`/code-review` に任せず自分で受け持つ。
