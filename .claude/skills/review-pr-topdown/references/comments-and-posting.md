# コメントの文面と投稿

PR の作成者は、指摘をコードの文脈の中で受け取りたく、解決策を押し付けられたくなく、答えても前に進まない問いで往復したくない。この節の決めごとは、その 3 点から来ている。

## 配置先

- 害が現れる行に行コメントとして置く。作成者がコードの文脈の中で受け取れるため
- PR 全体に関わる判断（課題の捉え方、必要性、方針、分解の妥当性）はレビュー本文に置く。一つのファイルに閉じるならファイルへのコメントでもよい
- 害が現れる箇所が diff に無いとき（diff の外への波及など）は、原因となる変更の行に置き、害が現れる箇所をパーマリンクで示す
- 1 つのコメントには 1 つの懸念だけを書く。スレッドごとに解決したかを追えるようにするため
- ほかのレビュアーが既に出した指摘は重ねない。加えるのは、新しい根拠があるときだけにする

ファイルへのコメントなど GitHub API の制約は、開発担当の作法の GitHub API の制約の項に従う。

## 文面

- 観察（どこで何が起きるか）、害（誰が・どの条件で・何に困るか）、満たしてほしい条件、の順に書く。直し方は作成者に委ねる。直し方の例を添えるときは、例であることを明記する
- 方針への疑問は、比べた代替案とその利点・代償を示し、PR の方針を選んだ理由を尋ねる形にする。代替案への変更を求める形にしない
- 問いには、答えの候補ごとに何が変わるかを添える
- 各コメントで、修正を求めるのか、求めないのか（参考・確認のみ）を明示する。作成者が優先度を判断でき、レビューの種類もそれで決まるため
- レビュー本文には全体の判定を書き、指摘の中身は行やファイルのコメントに任せて繰り返さない。作成者に同じ指摘を二か所で読ませないため。確かめられなかった範囲が作成者の受け取り方を左右するとき（Approve だが一部は未検証、など）は、それも書く
- 文面に指摘を受けたら、既存の文面に継ぎ足さず白紙から起こし直す。継ぎ足すと、指摘を受けた元の組み立てが残るため

## レビューの種類

- 残るコメントのうち、回答や対応次第で修正が入りうるものが 1 つでもあれば Comment
- 残るコメントがいずれも修正を求めないとき（コメントが無いときを含む）に限り Approve とし、本文に判定を伝える一言を添える
- 種類も、配置先・文面と同じくユーザーの合意を得る

## 投稿の手順

1. ユーザーが配置先・文面・種類に合意し、投稿を承認する
2. 投稿の直前に PR の head の SHA を取得し、判断したときの SHA と比べる。違えば投稿せず、SKILL.md の約束に従って見直す
3. 判断した SHA を commit_id に指定し、本文と行コメントを 1 つのレビューにまとめて提出する。commit_id を固定すると、確かめた版に対してコメントが付く。まとめて出すと、作成者への通知が 1 回で済む
4. 提出後、コメントが意図した行に付いたかを確かめ、レビューの URL をユーザーに示す
