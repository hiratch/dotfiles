# 補いの確認（diff を 1 行ずつ読む）

課題の木を辿る判断（判断の核）の補い。topdown のセルフレビューとレビューが、背景の開発担当のサブエージェントに渡す。木の判断は PR が述べた分解から組んだ節を辿るので、どの節にも結び付かない変更と、行ごとの文言や整いの問題は、原理的に届かない。それを、diff を 1 行ずつ読んで拾う。

木の判断（課題、必要性、方針、根拠、追随、分解の妥当性）はしない。それはメインが判断の核で受け持ち、ここで重ねると、行ごとの点検が木の判断の代わりになって、判断の順序（上流から）が崩れるため。

## 問うこと

diff の変えた行をすべて読み、次の 3 つだけを問う。

- 変更の説明: diff にある変更のそれぞれが、どの決定によるものかを、読み手が Description・コミットメッセージ・コード（コメント）のどこかで辿れるか。説明の無い変更（記載漏れ）と、振る舞いを変えるのに理由が書かれていない変更を挙げる。述べられていない変更は、木のどの節にも現れないため
- コメントと docstring: diff の中のコメント・docstring・識別子が述べることが、コードの取りうる場合（境界、最初と最後、空の入力など）で正しいか。同じ語が、同じファイルの別の記述と同じ範囲を指しているか。コードが自ら語れない理由（採らなかった設計、制約）が、コードから辿れる場所にあるか（基準は開発担当の作法の情報の置き場所）。文言の正しさは、振る舞いが契約を満たすかという木の問いからは見えないため
- 行の整い: 命名、構造、重複（同じ判断の二通りの書き方、同じ条件の分岐の重複、到達しない検査）。基準は開発担当の作法の可読性の項

生成物（再生成した期待値、ロックファイルなど）は、行を読まず、何をなぜ再生成したかが説明されているかだけを問う。生成物に紛れた意味の変化は、判断の核の「機械的な変更に紛れた意味の変化」で受け持つため。

## 根拠の基準

- 指摘は、対象のコードが現に持っている性質に限る。将来の変更を仮定した懸念や、改変したコードでの観測は指摘にしない
- 提示の前に、根拠と深刻度を一文で言えることを確かめる。言えないものは指摘にしない
- 確かめて問題の無かったものは書かない。メインとユーザーが読む量を、指摘だけにするため

## 渡すもの・返すもの

- 受け取るのは、PR（またはブランチ）、判断する head の SHA、このファイルの場所、書き出し先だけ。メインの判断や課題の木は受け取らない。行ごとに独立に読むため
- コードは固定した SHA の git のオブジェクトで読む。セルフレビューでは途中で作業ツリーが変わるため
- 書き出し先には、指摘ごとに、箇所（ファイルと行）、3 つの問いのどれか、何が起きているか、害（誰が何を誤るか）と確かさ、推奨する対応を書く
- 返す報告は、書き出し先のパスと指摘の件数だけにする。報告はメインの会話に届くので、要旨が含まれると、メインが節ごとの判断を終える前に読んでしまい、木の判断が行の細部に引き寄せられるため
