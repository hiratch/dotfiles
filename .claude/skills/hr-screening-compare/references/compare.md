# 従来のやり方と人事のスキルの比べ方（共通）

hr-screening-compare、hr-interview-prep-compare、hr-interview-evaluation-compare が共通に使う。比べるスキルの名前、従来のやり方、比べる項目は、それぞれの SKILL.md と references/items.md にある。

## 目的

人事のスキルが従来のやり方の代わりになるかを、同じ候補者の同じ段階の結果を並べて確かめ、スキルを直す材料と、従来のやり方を退かせる判断の材料を、候補者をまたいで貯める。比べた数を貯めること自体は目的ではない。

## 進め方

1. 始めるときに、背景で人事担当のサブエージェントにスキルを走らせることを示し、承認を求める（hook の確認ダイアログも出る）。
2. 人事担当を背景で起動する。渡すのは、候補者の記録の場所、ポジション、選考の段階、使うスキルの名前、書き出し先だけで、メインの判断や従来のやり方の結果は渡さない。サブエージェントは途中でユーザーに尋ねられないので、スキルがユーザーに諮るとしている点は問いとして書き出させ、推奨はそのまま出させる。資材と、候補者の記録の既存のファイルは変えさせない。返す報告は、書き出し先のパス、スキルの終わりの状態に達したか、ユーザーへの問いの数だけにさせ、推奨や判定の要旨を含めさせない。報告はメインの会話に届くので、要旨が含まれると、従来のやり方を進める前にメインが読み、従来のやり方の結果がそれに寄るため。
3. 従来のやり方で進める。ユーザーが今までしてきたとおり、地図が示す従来の手順のファイルと資材を読み、それに従ってユーザーと判断を詰める。この間、人事担当の本文、人事のスキル、比べる項目（references/items.md）、背景の書き出し先は読まない。新しい作法や比べる項目を知ったうえで従来のやり方を進めると、従来のやり方の結果がそれに寄り、差が見えなくなるため。
4. 従来のやり方の結果にユーザーが合意したら、比べる項目と背景の書き出し先を読み、項目ごとに両方の結果を並べる。
5. 違う項目を、両方の根拠（引用した原文、基準の文）とともにユーザーに示す。どちらが成り立つかを、メインは判定しない。メインは従来のやり方を進めた当事者で、自分の結果に寄せて読むおそれがあるため。引用が原文にあるか、決まった語が含まれるか、のように機械で確かめられることは確かめて添える。ユーザーが、項目ごとにどちらが成り立つかと、最終の判断を変えるかを決める。
6. 最終の判断に合わせて、外に出す記録を確定する。どちらの形で出すかはユーザーが決める。
7. 比べた記録を書き、まとめに 1 行足す。スキルや従来の手順に直すべき点に気づいたら所見に書き、直すかはユーザーが決める。

## 数え方

従来のやり方を退かせる判断に使うのは、従来のやり方の結果だけが成り立ち、ユーザーが最終の判断や外に出す記録に採った項目の数（スキルが落とした、または誤った項目）。これが続けて 0 で、スキルの結果に items.md が挙げる誤りの種類が出ていなければ、退かせる候補になる。退かせるかはユーザーが決める。スキルの結果だけが成り立った項目は、スキルの側の利点として数える。両方とも成り立たずにユーザーが直した項目は別に数え、スキルを直す材料にする。

## 記録の場所

候補者の情報を含むものは候補者の記録の中に置き、それ以外の場所には候補者を特定できることを書かない。

- 候補者ごと: 候補者の記録の下の `compare/<段階>/` に、背景の人事担当の書き出し（`skill/`）と、比べた記録（`comparison.md`。項目ごとの両方の結果、ユーザーの判定、数）を置く
- まとめ: `~/tmp/hr-compare/log.md` に 1 回 1 行（日付、ポジション、段階、比べた項目の数、両方が成り立つ・従来だけ・スキルだけ・両方とも成り立たない、の数、従来だけのうちユーザーが採った数、items.md の誤りの種類ごとの数（従来とスキルのそれぞれ）、示し方についてユーザーの印象、所見）。候補者の名前は書かない

## 約束

- 背景の人事担当には、書き出し先の外に書かせない
- 外に出す記録は、比べた後に確定する。比べて最終の判断が変わることがあるため
- 比べている途中で、従来の手順のファイルと人事のスキルを直さない。途中で直すと、同じ候補者での比べが成り立たなくなるため
