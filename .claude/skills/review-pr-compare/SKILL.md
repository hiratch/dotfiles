# review-pr-compare

## 目的と終わりの状態

review-pr-topdown（以下 topdown）を主にして他者の PR をレビューし、視点の違う補いとして review-pr-steps（以下 steps）と /code-review（ロジックを変える PR で）を併用し、その指摘を topdown の課題の木に統合して、漏れを投稿の前に補う。方式の視点が違えば拾う指摘も違うので、併用を前提にする。あわせて、補いだけが拾った指摘の数と、topdown がそれを落とした原因を、PR をまたいで記録する。原因は topdown を直す材料に、数は補いが要らなくなったかを見る材料にする。

終わったと言えるのは、topdown の終わりの状態（判断と根拠、確かめられなかった範囲、コメントの配置先・文面・レビューの種類への合意）に達して投稿し、記録を書いたとき。

投稿済みのレビューへの返信や追加のコミットへの対応には使わない。返信への応じ方の手順は、2 つの方式で同じファイルなので、比べても差が出ないため。

## 進め方

1. 始めるときに、このスキルが頼むサブエージェント（steps を走らせる開発担当）と、topdown が頼むサブエージェントを示し、承認を求める。
2. steps の事前確認を、背景の開発担当のサブエージェントに走らせる。渡すのは、PR、判断する head の SHA、steps の SKILL.md と手順書の場所（`~/.claude/skills/review-pr-steps/`）、書き出し先だけで、topdown の判断は渡さない。手順書の 1 周目（事前確認、Step 1〜5）だけを行い、PR への書き込みはせず、指摘の一覧を書き出させる（指摘ごとに、要旨・箇所・害・根拠・確かさ・推奨する対応。解消した候補と確かめられなかった範囲も）。コードは固定した SHA の git のオブジェクトで読ませる。レビューの間に PR が更新されうるため。返す報告は、書き出し先のパスと指摘の件数だけにさせ、指摘の要旨を含めさせない。報告はメインの会話に届くので、要旨が含まれると、topdown の判断を書き留める前にメインが読んでしまい、topdown が何を拾うかを測れなくなるため。
3. topdown の SKILL.md（`~/.claude/skills/review-pr-topdown/SKILL.md`）を読み、それに従って判断を進める。topdown の判断（課題の木、指摘の候補、解消した候補）を steps と同じ形で topdown.md に書き留めるまで、steps の一覧と /code-review の結果を読まない（判断の核の「上流の判断を固めた後に取り込む」より後になる）。先に読むと、木の上の層が補いの細部に引き寄せられ、topdown が何を拾うかを測れなくなるため。topdown が判断の核に従って /code-review を頼むときは、書き出し先をこの PR の記録のディレクトリの code-review.md にする。書き留めるのは、反証より前、ユーザーに示すより前に置く。コメントの文面と投稿は、5 の後に行う。
4. 書き留めたら、steps の一覧と /code-review の結果を読む。steps の指摘ごとに、同じ問題を指す topdown の指摘か解消した候補を名指しし、無ければ topdown が拾わなかったものとして、対応の控え（mapping.txt）に書く。/code-review の指摘ごとには、topdown と steps の両方について名指しし、どちらにも無ければ /code-review だけとして書く。名指しは、メインが「topdown も拾っていた」と寄せて数える偏りを、後から確かめられるようにするため。そのうえで、topdown が拾わなかった補いの指摘と、一方が指摘にし他方が解消したもの（両方の理由を添える）を、topdown の反証の依頼（判断の核が求める、候補をまとめて 1 回で頼むもの）に入れる。判定役を置かないので、自分が拾えなかった指摘をメインが割り引いて見るおそれを、会話の文脈を持たないサブエージェントの確かめで抑えるため。
5. topdown の示し方に従い、補いの指摘を、それが属する課題の木の節に入れて、topdown の判断と同じ形（害・根拠・対応の案と推奨）で示し、レビューに加えるかを合意する。topdown が拾わなかった補いの指摘は、反証で成り立たないとしたものも、その理由を添えてすべて示す。成り立つかの最後の判断をユーザーに残すため。topdown が拾わなかった補いの指摘には、どの補いが拾ったかと、topdown がその候補をどう扱ったか（挙げなかった、解消した〔その理由〕）を 1 行添える。topdown が何を落としたかをユーザーがその場で見られ、記録に書く原因の分類を確かめられるため。投稿の前に置くのは、取りこぼしをユーザーの名義で外に出す前に埋めるため。その後、topdown の「文面と投稿」に進む。
6. 記録を書く。振り分けの結果に、ユーザーに尋ねた示し方の印象（分かりやすさ・負荷）を添え、まとめの記録に 1 行足す。漏れを観測した観点は所見として書き、スキルを直すかはユーザーが決める。あわせて、topdown が落とした指摘（補いが拾ったもの、ユーザーの問いから出たもの、反証やユーザーの判断で逆転したもの）ごとに、原因を、木の作り方（根の取りこぼし、根の高さ、根の経緯、どの根にも属さない変更、期待される変更の抜け）、節の確かめ方の深さ、行の単位、のどれかに分けて書く。木の作り方を変えた効き目と、行の単位を何が受け持つかを、記録で判断するため。

## 数え方

補いを退かせる判断には、補いごとに、成り立ち、ユーザーがレビューに加えた指摘の数を使う。steps は、topdown が拾わず steps が拾った指摘の数で、/code-review も拾ったものを含める。両方が同じものを拾ったときに steps の数から抜くと、どちらの数にも入らず、両方とも要らないように見えるため。/code-review は、topdown も steps も拾わず /code-review だけが拾った指摘の数で、今の組み合わせに足す価値があるかを見る。/code-review を走らせなかった PR は、その数に入れない。steps を退かせた後は、/code-review も topdown が拾わなかったものを数え、その時点から数え直す。成り立っても、ユーザーが加えなかった指摘（害が小さい、この PR で扱うべきでないなど）は数えない。ユーザーとの議論で出た指摘は topdown の側に数える。退かせる判断は topdown とユーザーの協働で洗い出せているかで行うため。補いごとに、この数が直近 10 回続けて 0 になったら、その補いを退かせることをユーザーに提案する。10 回続けて 0 なら、その補いを並走させて補える漏れが残っていないと見なせるため。topdown が落とした指摘（補いが拾ったものと、ユーザーの問いから出たもの）は、topdown を直す材料として所見に書く。木の作り方と節の確かめ方の深さに起因する、topdown が拾わず steps が拾った指摘が 0 になった時点で、行の単位に残るものの受け持ち方（行の点検を戻すか、別の形にするか）を、記録を見てユーザーと決める。行の単位のものは木の判断から届きにくいことがあり、届くかどうかを記録で確かめてから決めるため。

## 記録の場所

組織のリポジトリの中身を含むので、公開の dotfiles には置かない。

- PR ごと: `~/tmp/review-compare/<リポジトリのディレクトリ名>-pr-<番号>/`。steps.md、code-review.md（/code-review の結果）、topdown.md（補いの結果を読む前に書き留めた topdown の判断）、mapping.txt（振り分けの名指し、出どころ、反証の結果、ユーザーの判断）を置く
- まとめ: `~/tmp/review-compare/log.md` に、PR ごとに 1 行（日付、PR、両方・topdown の側だけ・topdown が拾わず steps が拾った成り立つ指摘の数、そのうちレビューに加えた数、ユーザーの問いから出た指摘の数、topdown が落とした指摘の原因ごとの数（木の作り方・節の確かめ方の深さ・行の単位）、示し方の印象、時間の内訳、所見、/code-review だけの成り立つ指摘の数とそのうちレビューに加えた数〔走らせなかった PR は「—」〕）。時間の内訳は、記録を書く直前に `~/.claude/skills/review-pr-compare/scripts/review-time review-pr-compare` の出力をそのまま写す（「不明」と出たらそれを写す）。承認の待ち、ユーザーの思考の時間と往復の数、待ちの後の思考の時間を、手当ての前後で同じ物差しで比べるため

## 約束

- steps と /code-review のサブエージェントには、読み取りだけをさせる（編集・コミット・PR への書き込みをしない）
- topdown の約束（PR に書き込む操作はユーザーの承認の後で、直前に head を確かめる。他者向けの文面の手順。Comment と Approve の選び方）はそのまま守る
