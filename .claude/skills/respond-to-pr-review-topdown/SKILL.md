# respond-to-pr-review-topdown

## 目的と終わりの状態

ユーザーが指摘の中身と妥当性を理解して対応を選び、それを PR に反映して、reviewer が懸念の解消を少ない手間で確かめられ、後の読み手がなぜその形になったかを辿れる状態にする。

終わったと言えるのは、その回に応じる指摘のすべてで、合意した対応を終え（修正は push 済み）、返信を投稿し、Description が今の head と合い、再レビューを依頼するかをユーザーと決めたとき。PR を作り直すと決めたときは、[references/continue-or-recreate.md](references/continue-or-recreate.md) の受け渡しを終えたとき。

## 進め方の前提

- 返信はユーザーの名義で出るので、ユーザーは指摘を理解してから対応を選びたい。理解の材料と対応の案を一度に出すと、理解より先に案の評価を強いられる。一度に受け取れる量にも限りがある
- モデルには、レビューの指摘に狭く応じ、設計を問い直さない傾向がある（Claude Opus 5.5 System Card §2.3.3）。1 件ずつその場で直すと、同じ原因のほかの現れや、方針から来ている問題が残る

## 入口

依頼の言い方ではなく、PR の今の状態から応じる範囲を決める。行のスレッドに加えて、レビュー本文と PR の会話のコメントも見る（全体への指摘はそこに書かれる）。reviewer ごとのレビューの状態と、各コメントが付いた commit から今の head までの変化も見る。最後の発言が reviewer にあるものが対象になる。

スレッドごとの理解・妥当性・合意した対応・修正のコミット・返信の状態を、セッションの scratchpad のファイルに控える。会話が圧縮されても合意を失わないため。セッションをまたいだら、投稿済みの返信と現物から組み直す。

## 指摘の捉え方

指摘は、PR の述べることと同じく主張として扱い、判断の核（`~/.claude/skills/review-pr-topdown/references/pr-judgment.md`）の「何を判断するか」に沿って現物と突き合わせる。妥当性は、現物で成り立つ・成り立たない（反する観察を示す）・好みや慣習でどちらにも害が無い・判断できない（何があれば判断できるか）のいずれかとして、根拠の参照と確かさを添えて示す。

判断の核の「候補を指摘にする条件」は、応じるかどうかの関門にしない。あれは自分の候補で相手の注意を使わないための条件で、既に出された指摘には応じる必要があり、作成者が当てると自分の実装を守る向きに偏る。害は、reviewer の懸念を言葉にして理解するためと、対応の重さを決めるために使う。

対応を考える前に、その回の指摘を並べて、同じ原因から来ている指摘（まとめて解消する）、下流に現れた指摘の原因が方針にないか、指摘された箇所と同じ判断を持つほかの箇所、今この PR で起きている問題か仮定の懸念か、を見る。上流（課題・必要性・方針）に触れる指摘があれば、[references/continue-or-recreate.md](references/continue-or-recreate.md) を読み、同じ PR で続けるかも判断する。

## ユーザーへの示し方

最初に 1 画面程度で、reviewer ごとの状態、指摘をまとめた群と各群の要旨、上流に触れる指摘の有無、示す順を示す。その後 1 群ずつ（目安として 5 件まで）、2 回に分けて示す。

1. 理解: 原文（日本語でなければ和訳も）、箇所のパーマリンクと、そのコードが何をしているか（ユーザーが PR の文脈を覚えていない前提で）とその後の変化、reviewer の懸念（誰が・どの条件で・何に困るか。reviewer が書いていなければ推定と示す）、妥当性と根拠、今起きている問題か仮定の懸念か
2. 対応: ユーザーが理解に応じた後で、案（直す、説明を置く、返信で答える、Issue にする、直さない、reviewer に問う、作り直す・分ける・閉じる）と推奨、上流と下流への影響

応じ方が一つに決まる群（誤字など）は、比べる案が無いので 1 と 2 をまとめてよい。

## 対応

ユーザーと合意したものだけを行う。

- 直すときは、判断の核の「直し方」に従う。直したら、指摘が成り立っていた条件で直ったことと、PR の根拠（Description の検証の結果や、振る舞いを変えないといった暗黙の主張）が今の head でも成り立つことを確かめる。修正が根拠の前提を崩しうるため
- reviewer が意図を読み取れなかった箇所は、後の読み手も読み取れない。返信で説明して終えず、開発担当の作法の情報の置き場所に説明を置き、返信ではその場所を示す
- 好みや慣習の指摘で、どちらにも害が無ければ、reviewer に合わせることを推奨にする。コードを保守し続けるのは reviewer の側で、合わせる代償は小さいため
- 方針を変える対応では、self-review をやり直すかをその場で決める。やり直すなら、Description と返信はその後に書く。self-review が書くことを変えるため
- Description の主張が変わったら、`~/.claude/skills/prepare-pr-topdown/references/description.md` に従って書き直し、返信とまとめて校正に出す

## 返信

reviewer が懸念の解消を確かめるのに要ることと、後の読み手が経緯を辿るのに要ることだけを書く。

- 応じ方（直した、直さない、Issue にした、答え、問い返し）を一読で分かるようにする。直したなら、何をどこで直したか（一句と、コミットや行のパーマリンク）と、diff から読めないこと（提案と違う形にした理由、同じ判断を当てたほかの箇所、何で確かめたか）を書く
- 直さないなら、reviewer が自分で確かめられる観察を根拠にする。方針への異論には、比べた代替案と代償を示し、相手が違うと見ているのが事実か重み付けかを問う。意図の説明だけで退けると、reviewer には確かめる手段が無い
- 問い返すのは答えで対応が変わるときに限り、答えの候補ごとに何が変わるかを添える
- 将来の対応を約束しない。約束は reviewer にとって追跡すべき負債になり、果たせないと信頼を損なう。今起きている問題でこの PR の範囲の外なら Issue にしてリンクし、仮定の懸念なら確かめた事実（今どうなっているか、どの条件で問題になるか）の共有にとどめる
- Resolve は reviewer に任せる。解消したかを判断するのは reviewer で、作成者が閉じると返信が畳まれて見落とされうるため。慣行が違えば従う

その回の返信は、pending のレビューにまとめて（GraphQL の `addPullRequestReviewThreadReply` に pending のレビューを渡し、COMMENT で submit する）1 回で出す。reviewer への通知を 1 回にし、途中の状態を読ませないため。作り直す・閉じるという決定と、reviewer の続きの作業が待っている答えは先に出す。

## 再レビューの依頼

要るかをユーザーに諮る。修正を求める指摘に応じたとき、Approve の後に軽微でない変更を入れたとき（承認がその変更を含まない）は要る。

依頼は pr-workflow-guard が self-review の記録と照合し、記録の後に変更があれば、やり直さずに進めるかをユーザーに問う。それに答えられるよう、依頼の前に、記録の後に変わったファイルと、それぞれを何でどこまで確かめたかを示す。このスキルからは記録を書かない。記録は self-review を済ませたことを表し、書くと hook の知らせが消えるため。

## 崩さない順序

1. 理解をユーザーと合わせてから、対応の案を出す（理由は「進め方の前提」）
2. 上流に触れる指摘への対応（作り直すかを含む）を決めてから、下流の指摘に応じる。上流への応じ方で、下流の指摘の意味が変わったり消えたりするため
3. 修正を push してから、それを指す返信を出し、その後は履歴をユーザーと合意せずに書き換えない。リンク先の無い返信を読ませたり、reviewer が前回からの差分を見る手段を崩したりするため
4. 修正・返信・Description がそろい、今の head で CI が終わってから、再レビューを依頼する。依頼は「次を見てよい」という合図で、reviewer は CI と Description を最初に見るため

## 約束

- GitHub への書き込みは、書き込む内容そのもの（訳文を含む）をユーザーが見て承認してから行う
- 書き込む直前に、head が、文面を現物と突き合わせたときの SHA から変わっていないかを確かめる。変わっていれば書き込まず、差分を見て文面を確かめ直す
