# 同じ PR で続けるか、作り直すか

上流（課題・必要性・方針）に触れる指摘に応じるときに、この PR で続けるか、作り直す・分ける・閉じるかを決め、作り直すなら prepare-pr-topdown に受け渡す。

## 基準

既定は同じ PR で続け、主張が変わった Description の節を書き直す。方針が変わっても、その理由は reviewer とのスレッドにあり、同じ PR なら reviewer は自分の問いへの答えをその場で確かめられ、後の読み手は変更と理由を一か所で辿れるため。

作り直すのは、課題の根が変わるとき、すなわち Description の冒頭が言い切る「なぜ」と閉じる Issue が別のものになるとき（現物を見たら別の現象だった、など）に限る。前の議論は別の課題についてのものになって次の版を読む量を増やすだけになり、タイトルや Issue からのリンクも別の課題を指し続けるため。

- PR が複数の課題を抱えていると分かったら、この PR が受け持つ課題を残し、ほかを新しい PR に分ける。この PR のタイトルと Description は、残す課題に合わせて書き直す
- 必要性が否定されて解かないと決めたら、閉じる

## reviewer に伝える

作り直す・分ける・閉じると決めたら、その回のほかの返信を待たずに、この PR で決めたことと理由になった観察を伝える。reviewer が意味を失う版を読み続けないため。閉じるのはこの返信と同時でよい。新しい PR の本文から前の PR を参照すれば、前の PR のタイムラインに参照が出る（GitHub のイベント種別 cross-referenced）ので、前の PR に後からリンクを書き足さなくても辿れる。

## prepare-pr-topdown への受け渡し

作り直す PR と分けて出す PR は、prepare-pr-topdown の流れ（draft PR、self-review、Description の確定、reviewer の指定）で出す。前のレビューで分かったことが新しい PR の self-review と Description に入るよう、次を控えのファイルに書き、その場所をユーザーに示す。

- 前の PR の番号と、作り直す理由になった観察（現物で確かめた課題）
- 前のレビューの指摘のうち、新しい PR にも当てはまるもの。self-review で、新しい PR がそれに応えているかを確かめるため
- 前の PR の捉え方や方針と、それを採らない理由。Description の「選ばなかった代替案」に当たり、前の reviewer がまず問うため
- 前の reviewer。前の議論を知っているので、新しい PR の reviewer の案になる
